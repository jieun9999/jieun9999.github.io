## 들어가며

위블로그는 키워드를 입력하면 글감 후보와 설명·목차·출처를 먼저 준비하고, 사용자가 고른 글감으로 본문을 생성하는 서비스입니다. 제가 직접 부동산 글감을 검수하다 보면, 제목에서부터 멈추는 경우가 많았습니다.

> 송도 분양 예정 아파트 학군 좋은 단지를 찾는 기준과 확인 방법
>
> 송도 분양 예정 아파트 청약 준비를 위한 핵심 정보

무슨 주제인지는 알겠는데, 별로 클릭하고 싶지 않았습니다. 제목은 길었고, 끝에는 ‘확인 방법’, ‘선택 기준’, ‘핵심 정보’ 같은 표현이 붙었습니다. 여러 글감을 나란히 놓으면 서로 다른 내용을 다루는데도 비슷한 안내문처럼 보였습니다.

PoC 엔지니어는 저 혼자였고, 거의 주 단위로 실험한 내용을 운영에 반영했습니다. 하지만 무엇을 고쳐야 하는지 파악하는 데는 시간이 많이 걸렸습니다. 제목이 어색한 문제, 목차가 원래 질문에서 벗어나는 문제, 필요한 자료가 없는 문제가 함께 나타났기 때문입니다.

이 글에서는 그중 제목을 바꾼 과정을 설명합니다. 직접 사용하며 느낀 불편에서 출발해 생성 지시와 코드를 확인하고, 같은 글감으로 제목을 다시 만들어 비교했습니다.

## 1. 제목이 마음에 들지 않아 글감을 제외했습니다

당시에는 **글을 생성하기 전, 글감 카드에서 제목을 수정할 수 없었습니다.** 생성한 글의 제목은 수정할 수 있었지만, 글감을 고르는 단계에서는 바로 고칠 수 없었습니다.

그래서 제목이 마음에 들지 않으면 글감 카드 자체를 제외하는 경우가 많았습니다. 제목 한 줄의 문제가 어떤 글을 만들지 선택하는 데 영향을 주고 있었습니다.

| 사용 단계 | 당시 할 수 있던 일 | 제목이 마음에 들지 않을 때의 문제 |
| --- | --- | --- |
| 글감 검수 | 설명·목차·출처를 보고 승인하거나 제외 | 제목을 바로 수정할 수 없었습니다. |
| 본문 생성 이후 | 생성한 글의 제목 수정 | 글감을 고르는 시점의 불편은 남아 있었습니다. |

제목을 더 자극적으로 만드는 것보다, 고르기 전에 어떤 정보를 얻을 글인지 알 수 있어야 했습니다. ‘청약 준비를 위한 핵심 정보’보다 ‘청약 일정’이, ‘학군 좋은 단지를 찾는 기준과 확인 방법’보다 ‘학군 좋은 단지’가 제공할 답을 직접 보여줍니다.

## 2. 제목은 생성 단계를 거치며 다시 만들어지고 있었습니다

생성 코드를 확인하면서 먼저 봐야 했던 것은 **제목을 만드는 곳이 한 군데가 아니라는 점**이었습니다. 키워드로 초기 제목을 만들고, 자료를 모아 목차를 작성한 뒤 제목을 다시 만들었습니다.

```plaintext
키워드 → 초기 제목 생성 → 출처 수집·목차 작성 → 최종 제목 재생성
```

수정 전 코드에서 확인한 지시는 다음과 같습니다.

| 생성 단계 | 기존 지시 | 장황한 제목으로 이어질 수 있는 지점 |
| --- | --- | --- |
| 초기 글감 생성 | 키워드를 방법·순서·비교·주의점 등의 범주로 나누고 ‘안내문 제목’ 작성 | 구체적인 질문보다 범주와 안내 표현이 앞서기 쉽습니다. |
| 목차 이후 제목 생성 | 목차를 대표하는 제목 작성 | 여러 항목을 한 제목에 담으려다 나열이 길어질 수 있습니다. |
| 글감 카드 반영 | 목차 이후 생성한 제목으로 갱신 | 초기 제목만 바꿔도 최종 화면에서는 다시 달라질 수 있습니다. |

학군, 단지, 선택 기준, 확인 방법을 모두 대표하려다 보면 제목도 여러 항목을 이어 붙인 형태가 됩니다. 화면에서 본 장황한 제목을 설명할 수 있는 지점이었습니다.

**각 단계에서 제목에 남길 한 가지 답을 정하지 않으면, 다루는 내용을 담을수록 제목은 길어질 수 있었습니다.** 그래서 초기 제목만 짧게 쓰게 하는 대신 두 생성 단계의 기준을 함께 바꿔야 했습니다.

개별 글감의 모든 중간 제목을 추적해 단계마다 길어졌다고 측정한 것은 아닙니다. 화면의 결과와 수정 전 생성 지시를 함께 보고 확인한 개선 지점입니다.

## 3. 짧게 줄이거나 물음표를 붙이는 것으로는 부족했습니다

‘확인 방법’을 ‘어떻게 확인하나요?’로 바꾸면 문장은 조금 부드러워집니다. 하지만 독자가 찾던 답까지 잘 드러나는 것은 아니었습니다.

학군 좋은 단지가 궁금한 사람에게 필요한 것은 단지 정보입니다. 제목을 ‘학군은 어떻게 확인하나요?’로 바꾸면, 단지를 찾던 질문이 조회 방법을 묻는 질문으로 바뀝니다. 말투는 자연스러워졌어도 다른 답을 제공하는 글이 되는 셈입니다.

실제 중간 결과도 질문형에 치우쳤습니다. 비교 기록의 v9에서는 질문형이 여전히 많았고, ‘학군과 아파트 가격’을 ‘학교와 집값 정리’처럼 바꾸는 문제도 남았습니다. 자연스럽게 쓰려다 분야에서 익숙한 표현까지 바꾼 것입니다.

GTX-B 글감에서는 다음과 같은 변화가 있었습니다.

| 단계 | 실제 제목 |
| --- | --- |
| 기존 | 송도 입지 분석 실전 체크리스트와 적용 방법 |
| 직전 결과(v10) | 송도 입지 분석 GTX-B 영향과 5공구 체크 방법 |
| 최종 비교 결과(v11) | 송도 GTX-B 개통이 입지 가치에 미치는 영향 |

직전 결과에는 GTX-B라는 구체적인 대상이 들어갔지만, ‘영향’과 ‘체크 방법’이 섞여 있었습니다. 최종 결과는 개통과 입지 가치의 관계를 직접 드러냈습니다. 제목을 줄이는 것보다 **어떤 답을 제공할 글인지 정하는 것**이 먼저였습니다.

이 차이를 보면 모든 제목에 같은 말투를 적용하기 어렵습니다.

| 독자가 찾는 것 | 필요한 답 | 자연스러운 표현 방향 |
| --- | --- | --- |
| 구입에 필요한 자금 | 금액에 대한 직접적인 답 | 자금은 얼마나 있어야 하나요? |
| 청약 시기·학군 좋은 단지 | 일정·목록 | 청약 일정, 학군 좋은 단지 |
| 실제로 살아본 만족·불편 | 경험 자료 | 실거주 후기, 생활의 장단점 |

첫 번째는 질문으로 쓰는 편이 자연스럽지만, 두 번째는 정보의 이름만으로도 충분합니다. 세 번째는 경험을 다루는 글이라는 점이 드러나야 합니다.

**질문형·정보형·후기형을 나눈 이유도 이 때문입니다.** 서로 다른 답을 찾는 글감에 하나의 안내문 말투를 적용하지 않도록, 원하는 답에 맞춰 표현을 선택하게 했습니다.

## 4. 찾는 답에 따라 제목 형식을 고르게 했습니다

기존에도 제목 생성에는 Grok을 사용했습니다. 이번 변경의 중심은 모델 교체가 아니라, Grok에 주는 입력과 판단 순서였습니다.

**Grok의 제목 생성 프롬프트 안에서 형식을 먼저 고르고 제목을 쓰도록 지시했습니다.** 별도 분류기가 형식을 배정하는 구조는 아닙니다.

Grok이 입력과 목차를 보고 어떤 답을 찾는지 판단한 뒤, 그 답을 드러내는 형식으로 제목을 작성합니다. **이렇게 하면 제목을 특정 어미나 문장 틀에 맞추지 않고, 본문에서 다룰 내용에 맞는 형태로 자연스럽게 생성하도록 할 수 있습니다.** 청약 일정은 정보형으로, 직접적인 답이 필요한 내용은 질문형으로, 경험 자료를 다루는 내용은 후기형으로 표현할 수 있습니다.

여기서 세 형식은 고정 템플릿이 아니라 선택 기준입니다. 무엇을 알려줄 수 있는지가 먼저이고, 제목의 형태는 그에 따라 달라집니다.

### 전체 제목 생성 흐름과 Grok의 역할

최종 제목 모델이 읽는 것은 완성된 발행 글 전체가 아닙니다. **출처 원문으로 목차를 작성·검증하고, 제목 모델에는 그 목차를 전달합니다.** 본문으로 작성할 내용과 제목을 같은 근거에 맞추는 흐름입니다.

```plaintext
타깃 키워드·사람이 저장한 문장
  ↓
Grok: 공통 제목 원칙으로 초기 글감 생성
  ↓
출처 원문 수집 → 목차 작성·검증
  ↓
Grok: 입력과 검증된 목차를 함께 확인
      → 어떤 답을 찾고, 제공할 수 있는지 판단
      → 질문형·정보형·후기형 중 적합한 형식 선택
      → 제목과 입력 충족 평가 반환
  ↓
코드: 응답 검증·저장 문장 보존
  ↓
확정 제목을 글감 카드·콘텐츠 계획에 반영
  ↓
본문 생성·재작성에서도 확정된 한글 제목 유지
```

| 최종 제목 생성 입력 | 사용하는 목적 |
| --- | --- |
| 타깃 키워드 | 원래 무엇을 찾으려던 글감인지 확인 |
| 사람이 저장한 문장형 입력 | 질문의 대상·조건·말투 보존 |
| 검증된 목차의 항목·설명·출처 연결 | 본문으로 작성할 내용과 근거 범위 확인 |
| 해당 글감의 독자 질문 | 저장 문장이 없을 때 표현 참고용으로 사용 |

독자 질문은 표현을 참고하는 자료입니다. 질문에만 있는 숫자나 주장을 사실 근거로 쓰거나, 목차에 없는 내용을 제목에 추가하도록 하지는 않았습니다.

### 형식은 단어보다 원하는 답을 기준으로 골랐습니다

| 형식 | 프롬프트의 선택 기준 | 필요한 근거 |
| --- | --- | --- |
| 질문형 | 금액·가능 여부·선택처럼 직접적인 답을 구함 | 해당 질문에 답할 수 있는 목차와 출처 |
| 정보형 | 현황·목록·학군·가격·비교·일정을 찾음 | 제목에 제시한 정보를 제공할 수 있는 자료 |
| 후기형 | 실제 경험·만족·불편을 찾음 | 실제 경험 자료. 작성자가 직접 겪은 것처럼 꾸미지 않습니다. |

특정 단어로 형식을 결정하지는 않았습니다. ‘가격’이 들어 있다고 무조건 질문형이 되는 것은 아닙니다. 구입에 필요한 자금과 지역별 가격 비교는 원하는 답이 다릅니다. 형식별 할당 비율도 두지 않았습니다.

선택한 형식은 별도 필드로 저장하지 않았습니다. 생성된 제목과 응답을 비교했으며, 별도의 형식 분류 정확도를 측정한 실험은 아닙니다.

### 사람이 저장한 문장은 형식보다 우선했습니다

사람이 ‘송도 아파트 전세 시세 얼마인가요’라고 직접 입력했다면, 이미 무엇이 궁금한지와 말투가 들어 있습니다. 이를 ‘송도 아파트 전세 시세 확인하기’로 다시 조립할 필요는 없었습니다.

그래서 목차가 그 질문에 답할 수 있는지 확인한 뒤, 코드에서 저장 원문을 제목으로 사용했습니다.

```ts
if (input.titleInput) {
  draft.proposed_title = input.titleInput.text;
}
```

프롬프트에 보존 지시만 넣는 것으로 끝내지 않고 코드에서도 원문을 복원했습니다. 다만 질문을 보존한다고 답할 자료까지 생기는 것은 아니므로, 근거 확인이 앞에 있어야 했습니다.

### 모델의 판단과 코드의 검증을 나눴습니다

| 담당 | 실제 처리 |
| --- | --- |
| Grok | 입력과 목차를 보고 형식을 선택하고 제목을 작성합니다. |
| Grok | `input_coverage`의 `answered`와 `reason`으로 입력에 답할 수 있는지와 그 이유를 반환합니다. |
| 코드 | 답변 가능 평가가 누락됐는지 확인하고, 답할 수 없다는 응답은 보류합니다. |
| 코드 | 충족 평가 후 사람이 저장한 문장을 제목으로 복원합니다. |
| 코드 | 현황을 찾는 입력을 조회 방법 제목으로 바꾸는 일부 명확한 의도 변경을 차단합니다. |

입력 충족 평가는 저장 문장뿐 아니라 비어 있지 않은 명사형 키워드에도 적용했습니다. 처음부터 조회 방법을 요청한 입력이나 사람이 직접 저장한 문장은 구분했습니다. 코드 검증은 일부 명확한 오류와 보존 규칙을 처리하며, 모든 의미 판단을 대신하지는 않습니다.

## 5. 같은 글감 21개로 제목을 다시 만들어봤습니다

바꾼 기준은 기존 부동산 글감 21개로 비교했습니다. **목차와 출처를 고정한 상태에서 실제 Grok 제목 생성 단계를 다시 실행했습니다.** 자료까지 바꾸면 제목 지시를 바꾼 효과와 자료가 달라진 효과가 섞이기 때문입니다.

## 6. 고친 제목을 운영에 반영하고, 이후 생성에서도 유지했습니다

제목 작성 원칙은 초기 글감 생성과 목차 이후 제목 생성에 함께 적용했습니다. 사람이 저장한 문장도 필요한 단계까지 전달했습니다.

이후 본문 생성과 재작성에서는 목차와 함께 확정한 한글 제목을 유지했습니다. 본문 모델이 새 제목을 반환하더라도 계획에 확정된 제목이 있으면 그 제목을 사용하도록 했습니다.

```ts
export function publicationTitle(
  generated: string | undefined,
  plan: { proposed_title: string } | null,
  lang = 'ko',
): string | undefined {
  if (lang !== 'ko') return generated;
  return plan?.proposed_title.trim() || generated;
}
```

처음 문제를 확인할 때는 제목을 만드는 곳이 여러 군데였습니다. 수정할 때도 그 경로를 따라가야 했습니다. 한 단계에서 제목을 잘 만들어도 다음 단계에서 바뀌면 검수한 결과를 유지할 수 없기 때문입니다.

| 반영·검증 항목 | 확인한 내용 |
| --- | --- |
| 생성 지시 | 초기 글감과 목차 이후 제목 생성에 같은 원칙 적용 |
| 후속 생성 | 본문 생성·재작성에서 확정된 한글 제목 유지 |
| 코드 검증 | 후속 변경에서 워커 빌드와 전체 테스트 1,160개 통과 기록 확인 |
| 운영 제목 반영 | 비교 대상 중 20개의 글감 제목과 콘텐츠 계획 제목 갱신 |
| 보존한 데이터 | 목차·설명·출처·게시물 유지 |
| 반영 후 확인 | API 재조회에서 글감 제목과 계획 제목의 일치 확인 |

테스트는 저장 문장 보존과 입력 평가 등 코드 동작을 확인한 결과입니다. 제목의 자연스러움이나 독자의 선택을 수치로 평가한 결과는 아닙니다.

## 마무리하며

처음에는 제목이 길고 딱딱하다는 문제가 눈에 들어왔습니다. 생성 지시와 결과를 비교하면서, 제목에 무엇을 더 담을지보다 어떤 답을 보여줄지를 먼저 정하도록 바꿨습니다.

**Grok이 입력과 검증된 목차에서 제공할 답을 판단하게 하니, 모든 제목을 안내문이나 질문형으로 맞출 필요가 없어졌습니다.** 일정은 일정으로, 비교는 비교로, 경험은 후기로 드러낼 수 있도록 했습니다. 본문으로 작성할 내용에 맞춰 제목 형태를 선택하게 한 것이 이번 변경의 핵심입니다.

실제로 ‘청약 준비를 위한 핵심 정보’는 ‘청약 일정’이 됐고, ‘학군 좋은 단지를 찾는 기준과 확인 방법’은 ‘학군 좋은 단지’가 됐습니다. 검색량·클릭률·검수 시간 개선은 측정하지 않았습니다. 이번에 확인한 범위는 같은 입력에서 나온 제목의 변화와 생성·운영 경로에 반영한 동작입니다.

제목이 필요한 답을 분명하게 보여줘도, 그 답을 담은 자료를 확보하지 못하면 글을 만들 수 없습니다. 다음 편에서는 글감의 질문이 실제 검색어에 전달되도록 바꾸고, 수집한 플랫폼 문서를 후보별로 배정하는 과정을 다룹니다.

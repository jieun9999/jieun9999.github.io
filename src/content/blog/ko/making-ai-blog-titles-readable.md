## 들어가며

위블로그는 키워드를 입력하면 글감 후보와 설명·목차·출처를 먼저 준비하고, 사용자가 고른 글감으로 본문을 생성하는 서비스입니다. 제가 직접 부동산 글감을 검수하다 보면, 제목에서부터 멈추는 경우가 많았습니다. 길고 딱딱해서 어떤 답을 얻을 글인지 한눈에 들어오지 않았습니다.

이 글에서는 사용 중 발견한 문제를 생성 지시와 코드까지 따라가 개선한 과정을 설명합니다. 특히 **어떤 판단을 LLM에 맡기고, 어떤 동작을 코드로 처리했는지**에 초점을 맞췄습니다. 마지막에는 기존 글감 21개로 추가 재현한 전후 제목을 모두 비교합니다.

## 1. 제목 때문에 제외한 글감에서 생성 경로를 들여다봤습니다

### 제목을 고칠 수 없어 글감을 제외했습니다

당시에는 **글을 생성하기 전, 글감 카드에서 제목을 수정할 수 없었습니다.** 생성한 글의 제목은 수정할 수 있었지만, 글감을 고르는 단계에서는 바로 고칠 수 없었습니다. 그래서 제목이 마음에 들지 않으면 글감 카드 자체를 제외하는 경우가 많았습니다.

저장된 글감 제목을 보면 장황한 표현이 어떤 모습이었는지 알 수 있습니다.

| 지역 | 기존 글감 제목 |
| --- | --- |
| 용산 | 용산 재개발 아파트 매수 시 현금청산 위험과 계약 특약 확인법 |
| 병점 | 병점 오피스텔 실거주 후기에서 단지별 교통·생활환경·시세·주차 비교하기 |
| 한남 | 한남 보광동 임장 전에 구역별 재개발 상황과 빌라 매물 확인 방법 |

내용은 있어 보이는데, 별로 클릭하고 싶지 않은 제목이었습니다. ‘확인 방법’, ‘선택 기준’, ‘핵심 정보’ 같은 표현이 반복되고, 여러 글감을 나란히 놓으면 서로 다른 내용을 다루는데도 비슷한 안내문처럼 보였습니다.

### 문제가 겹쳐 있어 고칠 지점을 찾는 데 시간이 걸렸습니다

PoC 엔지니어는 저 혼자였고, 거의 주 단위로 실험한 내용을 운영에 반영했습니다. 하지만 무엇을 고쳐야 하는지 파악하는 데는 시간이 많이 걸렸습니다. 제목이 어색한 문제, 목차가 원래 질문에서 벗어나는 문제, 필요한 자료가 없는 문제가 함께 나타났기 때문입니다.

제목만 짧게 바꾸면 되는지, 목차가 잘못 만들어진 것인지, 자료부터 부족한 것인지 구분해야 했습니다. 그래서 화면의 제목뿐 아니라 생성 지시와 제목이 바뀌는 경로를 확인했습니다.

### 제목은 한 번만 만들어지는 것이 아니었습니다

키워드로 초기 제목을 만들고, 자료를 모아 목차를 작성한 뒤 제목을 다시 만들었습니다. 초기 제목만 고치면 마지막에 다시 덮어쓸 수 있는 구조였습니다.

```plaintext
키워드 → 초기 제목 생성 → 출처 수집·목차 작성 → 최종 제목 재생성
```

| 생성 단계 | 수정 전 지시·동작 | 확인한 개선 지점 |
| --- | --- | --- |
| 초기 글감 생성 | 방법·순서·비교·주의점 등의 범주로 나누고 ‘안내문 제목’ 작성 | 구체적인 질문보다 범주와 안내 표현이 앞서기 쉽습니다. |
| 목차 이후 제목 생성 | 목차를 대표하는 제목 작성 | 여러 항목을 한 제목에 담으려다 나열이 길어질 수 있습니다. |
| 글감 카드 반영 | 목차 이후 생성한 제목으로 갱신 | 두 생성 단계의 제목 기준을 함께 맞춰야 합니다. |

교통·생활환경·시세·주차를 모두 대표하려다 보면 제목에도 항목이 하나씩 붙습니다. 화면에서 본 장황함을 설명할 수 있는 지점이었습니다. **제목에 남길 한 가지 답을 정하지 않은 채 목차를 대표하려다 보니, 내용을 담을수록 제목이 길어질 수 있었습니다.**

이는 수정 전 코드와 화면의 결과를 함께 보고 확인한 개선 지점입니다. 개별 글감의 모든 중간 제목을 추적해 단계마다 길어졌다고 측정한 것은 아닙니다.

## 2. 제목 형식은 Grok이 고르고, 지켜야 할 규칙은 코드로 처리했습니다

### 짧게 줄이거나 물음표를 붙이는 것으로는 부족했습니다

‘확인 방법’을 ‘어떻게 확인하나요?’로 바꾸면 문장은 조금 부드러워집니다. 하지만 현황을 찾는 사람에게 필요한 것은 현황 자체입니다. ‘현황은 어디서 확인하나요?’로 바꾸면 찾던 답이 조회 방법으로 달라질 수 있습니다.

실제 중간 결과도 질문형에 치우쳤습니다. 초기 비교의 v9에서는 질문형이 여전히 많았고, ‘학군과 아파트 가격’을 ‘학교와 집값 정리’처럼 바꾸는 문제도 남았습니다. 자연스럽게 쓰려다 분야에서 익숙한 표현까지 바꾼 것입니다.

이 시행착오에서 구분할 필요가 있었던 것은 **독자가 원하는 답의 종류**였습니다. 금액을 직접 묻는 경우, 일정이나 목록을 찾는 경우, 실제 경험을 찾는 경우에 같은 안내문 말투를 적용할 필요는 없었습니다.

| 형식 | 선택 기준 | 표현 방향 |
| --- | --- | --- |
| 질문형 | 금액·가능 여부·선택처럼 직접적인 답을 구함 | 얼마나 필요한지, 가능한지, 어느 쪽이 나은지 묻습니다. |
| 정보형 | 현황·목록·학군·가격·비교·일정을 찾음 | 대상과 제공할 정보를 직접 드러냅니다. |
| 후기형 | 실제 경험·만족·불편을 찾고 경험 자료가 있음 | 실제 경험을 다루되 작성자가 직접 겪은 것처럼 꾸미지 않습니다. |

‘가격’이 들어 있다고 무조건 질문형으로 결정하지 않았습니다. 필요한 구입 자금과 지역별 가격 비교는 원하는 답이 다릅니다. 형식별 할당 비율이나 고정 어미도 두지 않았습니다.

### 입력과 목차의 의미를 읽는 일은 Grok에 맡겼습니다

기존에도 제목 생성에는 Grok을 사용했습니다. 이번에는 **Grok의 제목 생성 프롬프트 안에서 형식을 먼저 고르고 제목을 쓰도록 지시했습니다.** 별도 분류기가 형식을 배정하는 구조는 아닙니다.

| 최종 제목 생성 입력 | 사용하는 목적 |
| --- | --- |
| 타깃 키워드 | 원래 무엇을 찾으려던 글감인지 확인 |
| 사람이 저장한 문장형 입력 | 질문의 대상·조건·말투 보존 |
| 검증된 목차의 항목·설명·출처 연결 | 본문으로 작성할 내용과 근거 범위 확인 |
| 해당 글감의 독자 질문 | 저장 문장이 없을 때 표현 참고용으로 사용 |

Grok이 입력과 목차를 보고 어떤 답을 찾는지 판단한 뒤, 그 답을 드러내는 형식으로 제목을 작성합니다. **제목을 특정 문장 틀에 끼워 맞추지 않고, 본문에서 다룰 내용에 맞는 형태로 자연스럽게 생성하도록 한 것입니다.** 질문형·정보형·후기형은 그 판단을 돕는 기준입니다.

제목 모델이 완성된 발행 글 전체를 읽는 것은 아닙니다. 출처 원문으로 목차를 작성·검증하고, 그 목차를 제목 생성에 전달합니다. 독자 질문 역시 표현 참고용이며 사실 근거로 사용하지 않습니다.

### 한 글감이 제목이 되기까지: 단계별 타임라인

용산 글감 한 건을 따라가면 단계마다 어떤 데이터가 넘어가는지 볼 수 있습니다. 아래는 화면 캡처가 아니라 **저장된 입력·목차와 실제 재현 응답을 발췌한 데이터 스냅샷**입니다. 번호는 처리 순서이며, 단계별 소요 시간을 측정한 타임라인은 아닙니다.

| 순서 | 담당·처리 | 단계별 스냅샷 |
| --- | --- | --- |
| **01 · 입력** | 키워드와 저장 문장 전달 | **키워드:** 용산 재개발 아파트<br />**저장 문장:** 이 사례에는 없음 |
| ↓ **02 · 글감 제목** | 코드상 흐름: Grok이 초기 제목 생성 | **참고할 수 있는 보존 제목:** 용산 재개발 아파트 매수 시 현금청산 위험과 계약 특약 확인법<br />초기 생성 직후 응답은 확인되지 않아, 이 저장 제목이 초기 응답과 같다고 단정할 수는 없습니다. |
| ↓ **03 · 근거와 목차** | 출처 원문으로 목차 작성·검증 | **보존된 목차 항목:** “용산 재개발 아파트 매수 전에 현금청산 위험이 실제로 있나요?”<br />**설명 요약:** 조합원 지위 양도가 제한되는 위험을 출처로 설명<br />**연결 출처:** solnews.co.kr의 기사 URL<br />다른 항목에는 계약 특약과 공유지분 확인 사항이 포함돼 있었습니다. |
| ↓ **04 · 최종 제목** | Grok이 입력과 목차에서 필요한 답을 판단하고 제목 작성 | **실제 응답:** 용산 재개발 아파트 사면 현금청산 위험 있나요?<br />**입력 충족 평가:** answered = true<br />**reason 발췌:** “목차가 용산 재개발 아파트 매수와 관련된 현금청산 위험 존재 여부, 회피 조건, 특약, 공유지분 확인 사항을 직접 다루므로 검색 의도에 답한다.” |
| ↓ **05 · 코드 검증** | 필수 응답과 제목 검증·저장 원문 처리 | **실제 결과:** status = ready<br />**검증 후 제목:** 용산 재개발 아파트 사면 현금청산 위험 있나요?<br />이 사례에는 저장 문장이 없어 원문 복원은 적용되지 않았습니다. |
| ↓ **06 · 저장·후속 생성** | 확정 제목 저장, 본문 생성·재작성에서 유지 | **코드상 동작:** 확정된 proposed_title을 한글 제목으로 사용합니다.<br />이번 추가 재현은 05까지 실행했으며, 운영 저장과 본문 생성은 실행하지 않았습니다. |

01–03은 보존된 데이터를 읽은 것이며 이번에 초기 제목이나 목차를 새로 생성한 것은 아닙니다. 04–05에서 제목 생성·검증을 다시 실행했습니다. 형식 선택은 프롬프트 내부 지시이므로, ‘질문형으로 분류했다’는 별도 로그는 없고 실제 생성된 질문형 제목을 확인할 수 있습니다.



### 반드시 지켜야 할 동작은 코드로 처리했습니다

자연스러운 표현을 고르는 일과, 저장 원문을 유지하거나 필수 응답을 확인하는 일은 성격이 달랐습니다. 의미 판단은 Grok에 맡기되, 명확히 실행할 수 있는 규칙까지 프롬프트에만 의존하지 않았습니다.

| 판단·동작 | Grok에 맡긴 부분 | 코드로 처리한 부분 |
| --- | --- | --- |
| 제목 형식과 표현 | 입력과 목차를 읽고 적합한 형식·표현 선택 | 특정 단어로 형식을 강제하지 않습니다. |
| 입력에 답할 수 있는지 | `input_coverage`의 `answered`와 `reason`으로 평가 | 평가 누락을 확인하고, 답할 수 없다는 응답은 보류합니다. |
| 사람이 저장한 문장 | 그 질문에 답할 수 있는지 평가 | 충족 평가 후 저장 원문을 제목으로 복원합니다. |
| 원래 의도 유지 | 부족한 자료를 다른 질문으로 우회하지 않도록 판단 | 현황 요청을 조회 방법으로 바꾸는 일부 명확한 사례를 차단합니다. |
| 이후 생성 | 확정된 제목에 맞춰 본문 작성 | 본문 생성·재작성의 제목으로 확정 제목을 사용합니다. |

`input_coverage`는 **LLM의 의미 평가**입니다. 코드가 그 값을 확인한다고 해서 출처의 사실관계를 독립적으로 검증한 것은 아닙니다.

저장 문장은 형식 선택보다 우선합니다. 사람이 이미 작성한 질문을 모델이 선호하는 말투로 다시 쓰게 하지 않았습니다. 현황을 조회 방법으로 바꾸는 차단 규칙에서도, 처음부터 조회 방법을 요청한 입력과 저장 문장은 구분했습니다.

## 3. 같은 글감 21개로 제목을 다시 만들어봤습니다

### 짧아졌는지와 필요한 답이 드러나는지를 함께 봤습니다

용산 제목은 ‘위험과 계약 특약 확인법’을 나열하던 문장에서 ‘사면 현금청산 위험 있나요?’라는 직접적인 질문으로 바뀌었습니다. 성수 제목은 ‘현황 확인 방법’ 대신 ‘지구별 진행 상황’을 보여줍니다. 안산과 양평역 사례는 실제 경험을 다루는 후기형으로 생성됐습니다.

| 판단 기준 | 이번 결과에서 살펴본 지점 |
| --- | --- |
| 장황함 | ‘확인 방법’, ‘확인하기’ 같은 안내 표현과 불필요한 나열이 줄었는지 확인했습니다. |
| 자연스러움 | 질문형·정보형·후기형이 필요한 답에 맞게 쓰였는지 봤습니다. |
| 답의 명확성 | 무엇이 가능한지, 어떤 현황이나 경험을 제공하는지 제목만으로 드러나는지 확인했습니다. |
| 근거 범위 | 기존 목차 안에서 제목을 생성·검증했습니다. 표에 나온 금액·시점·전망의 현재 사실관계를 다시 조사한 결과는 아닙니다. |

모든 결과가 짧아진 것은 아닙니다. 계약금 사례처럼 질문을 구체화하면서 길이가 늘기도 했고, 명사 나열이 남은 제목도 있습니다. 길이만으로 성공 여부를 정하지 않고, 제공할 답과 표현을 함께 비교했습니다.

## 마무리하며

제목이 길고 딱딱하다는 문제에서 출발했지만, 해결하려면 무엇을 제목에 남길지 판단하는 과정과 그 판단을 유지하는 코드가 함께 필요했습니다.

**입력과 목차의 의미를 읽고 제목의 형태를 선택하는 일은 Grok에, 원문 보존·명확한 오류 처리·확정 제목 유지는 코드에 맡겼습니다.** 이 경계를 정하면서 본문으로 제공할 답에 맞춰 제목을 표현하고, 이후 생성 단계에서도 그 결과를 유지하도록 했습니다.

다음 편에서는 필요한 답이 실제 검색어에 전달되도록 바꾸고, 수집한 플랫폼 문서를 후보별로 배정하는 과정을 다룹니다.

> [!NOTE]
> 25분 동안 배포가 8번 나갔고, 그때마다 서비스가 끊겼습니다. 범인은 서비스명을 적지 않은 `docker compose up -d --force-recreate` 한 줄이었습니다.

회사에서 운영하는 블로그 마케팅 플랫폼에서는 ARM 서버 한 대(2 OCPU / 12GB) 위에 docker compose로 전체 스택을 올려 운영하고 있습니다. `main`에 머지되면 GitHub Actions가 서버에 SSH로 붙어 `git pull → build → up -d`를 돌리는, 아주 흔한 구성입니다.

그런데 개발자 둘이 붙어 연달아 머지하기 시작하니 문제가 드러났습니다. **배포할 때마다 서비스가 끊겼습니다.** 이 글은 그 원인을 끝까지 파고들어 blue-green으로 다시 세운 기록입니다.

---

## 1\. 발견 — 배포 시각과 장애 시각이 정확히 겹친다

먼저 실측입니다. 25분 동안 배포가 여덟 번 나갔습니다.

```plaintext
05:34  #142  3m27s  success
05:47  #144  1m34s  success
05:50  #146  1m53s  success
05:51  #147  4m27s  success
05:56  #145  2m18s  success
05:56  #149  3m11s  success   ◀── 05:58:54 장애가 이 런 안에서 발생
05:58  #148    50s  cancelled ◀── 대기 중 다음 런이 도착해 밀려남
05:59  #150  3m41s  success
```

`#148`이 취소된 건 `cancel-in-progress: false`의 정상 동작입니다. 대기 슬롯이 하나뿐이라 세 번째 런이 오면 대기 중이던 런이 취소됩니다. 즉 **배포가 이미 유실되고 있었습니다.**

그리고 `05:58:54`에 사용자 화면이 죽었습니다. 그런데 이상한 게 하나 있었습니다. **앱과 아무 상관 없는 정적 블로그까지 같이 죽었습니다.** 이 플랫폼에서 `{slug}.example.com` 으로 서빙되는 블로그는 Next.js 앱을 거치지 않고, 리버스 프록시가 빌드 산출물을 직접 내려주는 순수 정적 파일입니다. 앱이 재시작된다고 죽을 이유가 없습니다.

## 2\. 진짜 범인 — 죽은 건 앱이 아니라 리버스 프록시였다

에러 코드가 결정적인 단서였습니다. **502가 아니라 521**이었습니다.

| 코드    | 뜻                                 | 이 경우의 의미                   |
| ------- | ---------------------------------- | -------------------------------- |
| 502     | origin에 붙었는데 뒤가 죽어 있음   | 앱 컨테이너만 죽은 상태          |
| **521** | **origin에 TCP 연결 자체가 안 됨** | **80/443을 아무도 안 듣고 있음** |

`/api/auth/google/start` 같은 API 경로까지 521이 떴습니다. 앱만 죽었다면 프록시가 살아서 502를 돌려줬어야 합니다. 즉 죽은 건 뒤쪽 앱이 아니라 **진입점(Caddy)** 자체였습니다.

이 플랫폼에서 Caddy는 단순한 라우터가 아닙니다.

```plaintext
example.com          ──► caddy ──► admin:3000     (랜딩·로그인)
admin.example.com    ──► caddy ──► admin:3000     (슈퍼 어드민)
{slug}.example.com   ──► caddy ──► dist/{slug}/   ★ 정적 파일. 앱을 안 거침
커스텀 도메인          ──► caddy ──► dist/{slug}/   ★ 동일
```

**Caddy가 곧 블로그 웹서버입니다.** 그래서 Caddy가 죽으면 앱과 무관한 블로그까지 전멸합니다.

## 3\. 코드 점검 — 잠깐, 앱 한 줄 고친 배포가 db를 지운다고?

워크플로에서 배포를 수행하는 줄은 이것 하나였습니다.

```bash
docker compose -f deploy/compose.yml up -d --remove-orphans --force-recreate
```

**서비스명이 없습니다.** compose에서 이건 "전부"라는 뜻이고, 이 파일의 전부는 여섯 개였습니다.

| 서비스   | 역할                                           | 재생성되면                                                      |
| -------- | ---------------------------------------------- | --------------------------------------------------------------- |
| `db`     | Postgres(pgvector). sites·posts·schedules 전부 | **도미노의 첫 조각.** `depends_on` 연쇄로 api·admin까지 끌고 감 |
| `redis`  | BullMQ 큐 (`noeviction` + `appendonly`)        | api·worker가 healthy 대기로 묶임                                |
| `api`    | 내부 API(:8787). 외부 미노출, admin이 호출     | admin이 떠 있어도 데이터를 못 가져와 500                        |
| `admin`  | Next.js. 랜딩·온보딩·개인 어드민·슈퍼 어드민   | 유일한 사용자 대면 앱. 20~40초 공백                             |
| `worker` | Astro 빌드·예약 발행 잡 소비                   | 무해. 큐가 흡수해서, 뜨면 밀린 잡을 처리                        |
| `caddy`  | 80/443 바인딩 + **블로그 정적 서빙**           | **521.** 진입점이 사라짐                                        |

여기에 `--force-recreate`가 겹쳤습니다. 이 플래그는 "바뀐 것만 재생성"하는 판단 자체를 끕니다. compose는 평소 서비스의 해석이 끝난 설정 전체를 해시로 만들어 컨테이너 라벨(`com.docker.compose.config-hash`)에 저장해두고, 다음 `up -d` 때 비교해서 **달라진 것만** 다시 만듭니다. `--force-recreate`는 그 비교를 건너뜁니다. 공식 문서 표현 그대로 _"Recreate containers even if their configuration and image haven't changed."_

결과적으로 **앱 한 줄 고친 배포가 db와 Caddy까지 파괴하는 배포**가 되어 있었습니다.

### recreate는 restart가 아니다

여기서 한 가지를 짚고 가야 합니다.

```plaintext
stop  →  rm  →  create  →  start
             ▲
       이 구간엔 컨테이너가 아예 존재하지 않는다
```

`restart`는 프로세스만 다시 시작하고 컨테이너는 계속 존재합니다. `recreate`는 지웠다가 다시 만듭니다. Caddy가 이 구간에 있으면 호스트의 80/443을 **아무 프로세스도 바인딩하지 않습니다.** 방화벽 차단이 아니라 연결 자체가 거부되고, Cloudflare가 그걸 521로 표시합니다.

그리고 `depends_on` 연쇄가 이걸 초 단위에서 분 단위로 늘립니다.

```plaintext
 0s   db·redis  stop→rm→create→start
10s   ├─ db healthy 대기 (pg 부팅)
20s   api       stop→rm→create→start
40s   ├─ api healthy 대기
50s   admin     stop→rm→create→start
90s   caddy     stop→rm→create→start   ◀── 여기서만 521
```

| 대상                             | 죽는 구간               | 대략             |
| -------------------------------- | ----------------------- | ---------------- |
| 블로그 (정적)                    | caddy 재생성 때만       | **5~10초** (521) |
| 랜딩 · 개인 어드민 · 슈퍼 어드민 | db→api→admin→caddy 내내 | **60~100초**     |

블로그의 5~10초는 짧지만 사라져도 되는 시간은 아닙니다. 하루 여덟 번 배포하면 크롤러가 521을 받을 기회가 여덟 번 생기고, 이건 원래 0이어야 하는 숫자입니다.

## 4\. 설계 ① — 무엇을 2벌로 만들 것인가가 아니라, 무엇을 만들지 않을 것인가

blue-green이라고 하면 "앱을 두 벌 띄워서 번갈아 쓴다" 정도로 요약되곤 하는데, 실제로 설계할 때 시간을 가장 많이 쓴 건 **어디까지 복제하지 않을 것인가**를 정하는 일이었습니다.

표준 blue-green의 원리는 하나입니다.

```plaintext
                    ┌──────────────────────────────┐
   사용자 ────────► │  라우터 (Caddy/nginx/ALB)     │  ← 항상 살아있음. 전환 = 설정 flip
                    └───────┬──────────────┬───────┘
                            │ (활성)        │ (대기)
                    ┌───────▼──────┐  ┌────▼─────────┐
                    │  app  BLUE   │  │  app  GREEN  │   ← 무상태 앱만 2벌
                    └───────┬──────┘  └────┬─────────┘
                            └───────┬───────┘
                          ┌─────────▼─────────┐
                          │  DB / Redis  1벌   │   ← 상태 보유. 절대 2벌로 안 만듦
                          └───────────────────┘
```

**복제하는 건 무상태 앱 티어뿐입니다.** blue-green은 "앱 배포"의 무중단을 보장하는 기법이지, DB 재시작의 무중단을 보장하는 기법이 아닙니다.

### redis는 캐시가 아니라 큐다

```plaintext
command: ["redis-server", "--maxmemory-policy", "noeviction", "--appendonly", "yes", ...]
```

`noeviction` + `appendonly`는 "이 데이터는 절대 잃으면 안 된다"는 선언입니다. 안에 든 게 Astro 빌드 잡, 예약 발행 잡 같은 실제 작업 큐거든요. 2벌로 나누면 이렇게 됩니다.

```plaintext
blue-redis  [잡A, 잡B, 잡C]  ← blue-worker 가 처리 중
green-redis [           ]     ← 텅 빔

flip → green 으로 전환

green-worker 는 빈 큐를 봄  →  잡A·B·C 는 아무도 처리하지 않음
blue-redis 를 정리하는 순간  →  영구 유실
```

캐시라면 미스가 나도 다시 채우면 됩니다. 큐는 그럴 수 없습니다. **예약 발행된 글이 조용히 사라지고, 사용자는 원인을 알 수 없습니다.**

### db는 제품의 유일한 진실이다

`pgdata` 볼륨 하나에 sites·posts·schedules가 전부 들어 있습니다. 2벌로 만들면 전환 구간에 들어온 쓰기가 어느 쪽 db에 들어갔는지에 따라 갈리고, 롤백하면 그 사이 데이터가 통째로 사라집니다. 제대로 하려면 스트리밍 복제 + failover가 필요한데, 그건 blue-green이 아니라 **HA 구성**입니다. 배포 다운타임을 풀자고 꺼낼 물건이 아닙니다.

db·redis 말고도 공유 상태가 더 있습니다 — `dist`(Astro 산출물), OG 이미지, 업로드 파일, 도메인별 프록시 설정. 전부 worker가 쓰고 Caddy가 읽는 구조라 역시 쪼갤 대상이 아닙니다.

### 서비스별 결론

| 서비스    | 2벌?      | 근거                                                                     |
| --------- | --------- | ------------------------------------------------------------------------ |
| **admin** | **○ 2벌** | 유일한 사용자 대면 경로. 다운타임이 곧 장애                              |
| api       | ✕ 1벌     | 외부 미노출. admin만 호출하므로 재시작 20초는 admin이 흡수 가능          |
| worker    | ✕ 1벌     | **큐가 다운타임을 흡수한다.** 2벌이면 다른 버전 둘이 같은 큐를 먹는 위험 |
| db        | ✕ 1벌     | 단일 진실. 복제는 HA의 영역                                              |
| redis     | ✕ 1벌     | 큐. 쪼개면 잡 유실                                                       |
| caddy     | ✕ 1벌     | 라우터는 재시작 대상이 아니라 **reload 대상**                            |

worker가 특히 다행이었습니다. 큐 기반이라 **애초에 무중단이 필요 없습니다.** 내려가 있으면 잡이 쌓였다가 뜨면 처리됩니다.

> [!NOTE]
> "admin 2벌"이 상시 2개 가동을 뜻하는 것도 아닙니다. 평상시엔 한 개만 뜨고, 배포 1회당 1~2분만 겹칩니다. 2 OCPU / 12GB 한 대에서 서버 네이티브 arm64 빌드까지 돌리기 때문에, 상시 2벌의 메모리가 배포 시점 빌드 피크와 정면으로 부딪힙니다.

## 5\. 설계 ② — 라우터는 재시작하는 게 아니라 reload하는 것이다

Caddy를 재생성 대상에서 빼는 것만으로는 끝나지 않습니다. **배포마다 반영돼야 하는 것**이 있기 때문입니다 — 새로 만들어진 블로그의 도메인 설정, 그리고 ③에서 추가될 blue/green upstream.

reload는 재시작이 아닙니다.

```plaintext
   [caddy 프로세스 — 계속 살아있음, 소켓 계속 점유]
            │
      reload
            │
   ├─ 새 config 파싱 · 검증
   ├─ 검증 실패 → 옛 config 유지. 아무 일도 일어나지 않음
   └─ 검증 성공 → 새 config 활성화
            │
       처리 중이던 요청 ──► 옛 config 로 끝까지 완료
       새로 들어온 요청 ──► 새 config 로 처리
            │
   [소켓은 단 한 순간도 안 풀림]
```

포트가 비는 순간이 없으니 **521이 구조적으로 불가능**합니다. 게다가 `caddy validate`가 먼저 돌기 때문에 틀린 설정을 밀어도 서비스가 죽지 않습니다. 재생성은 정반대입니다 — 설정이 잘못되면 컨테이너가 못 뜨고 그대로 장애입니다.

여기서 좀 허무한 사실 하나. **이 reload 스텝은 워크플로에 원래부터 있었습니다.** 그런데 앞 단계에서 `--force-recreate`로 Caddy를 이미 죽여버려서, 무중단 도구를 갖춰놓고 그 효과를 스스로 없애고 있었습니다.

### 그런데 이 안전성은 reload 경로에서만 성립한다

`caddy validate`가 지켜주는 건 **이미 떠 있는 Caddy에 새 설정을 밀어 넣는 경우**뿐입니다. Caddy가 재생성되어 **처음부터 기동하는** 경로는 얘기가 다릅니다. 설정이 파싱조차 안 되면 컨테이너가 부팅에 실패하고, restart 루프에 빠지고, 80/443은 계속 비어 있습니다.

그래서 원칙을 하나 더 뒀습니다.

> **Caddy는 언제 기동하든 파싱 가능한 설정을 갖고 있어야 한다.**

upstream이 실제로 살아있는지는 그다음 문제입니다. 파싱만 되면 Caddy가 떠서 블로그(정적)는 정상 서빙되고 앱만 502가 됩니다. **전멸(521)과는 차원이 다른 피해**입니다. 그래서 배포 스크립트에 `--ensure` 단계를 두어, 활성 색 설정 파일이 없으면 먼저 만들어놓고 그다음에 `up -d`가 돌게 했습니다.

그리고 Caddy의 `depends_on: admin`도 지웠습니다. 앱 재생성이 Caddy로 번지는 경로였습니다.

## 6\. 설계 ③ — 순서를 뒤집는다: 죽이고 만들기 → 만들고 죽이기

앱 다운타임의 정체는 단순합니다. 재생성이 **죽이고 나서 만드는** 순서라는 것.

```plaintext
  stop      rm      create    start    Next.js 부팅    healthy
   │         │        │         │          │            │
   ▼         ▼        ▼         ▼          ▼            ▼
[admin 살아있음] ──── admin 이 존재하지 않음 ───── [admin 살아있음]
                  └──────── 20~40초 ────────┘
                              ▲
              caddy 는 살아있는데 보낼 곳이 없음 → 502
```

여기서 흔한 오해를 하나 짚고 갑니다. Caddyfile에는 이미 이런 게 들어 있었습니다.

```caddy
reverse_proxy {
	dynamic a { name admin  port 3000  refresh 5s  resolvers 127.0.0.11 }
}
```

`dynamic a`는 좋은 장치지만 **푸는 문제가 다릅니다.**

| `dynamic a`가  | 내용                                                              |
| -------------- | ----------------------------------------------------------------- |
| 푸는 것        | 새 컨테이너의 **IP가 바뀌어도** 5초 안에 따라간다 → 복구가 빠르다 |
| **못 푸는 것** | 컨테이너가 **아예 없는** 20~40초                                  |

대상이 없으면 IP를 아무리 정확히 추종해도 502입니다. **슬롯이 하나인 한 못 고칩니다.** 그래서 순서를 뒤집습니다.

```plaintext
기존 (kill → start)
  [blue 살아있음]────╳────────────[blue' 살아있음]
                    └── 다운 ──┘

blue-green (start → kill)
  [blue 살아있음 ─────────────────────]────╳
                  [green 준비 ──────────────────────]
                                    ▲ 여기서 전환
                    두 컨테이너가 겹치는 구간이 있음 → 다운 없음
```

### 전환 장치는 파일 한 장

이미 도메인별 설정을 `import`로 붙이는 패턴을 쓰고 있었기 때문에, 그걸 그대로 재사용했습니다. `active/admin.caddy` 파일 하나가 활성 색을 결정합니다.

```caddy
# 배포 스크립트가 이 파일만 다시 쓴다
(admin_upstream) {
	reverse_proxy {
		dynamic a { name admin-green  port 3000  refresh 5s  resolvers 127.0.0.11 }
		header_up Host {host}
	}
}
```

Caddyfile의 두 블록에서 인라인 `reverse_proxy`를 `import admin_upstream` 한 줄로 바꿨습니다. 네트워크 alias를 조작하는 방식도 가능했지만, 파일 + reload가 **전환 시점이 명시적**이고 롤백이 `git checkout` 수준으로 단순해서 이쪽을 택했습니다.

### 왜 0초인가

전 과정에서 "응답할 수 있는 admin"이 항상 최소 하나 존재합니다.

```plaintext
t0  blue 활성 · green 없음     caddy → blue     ✔ 응답 가능
t1  green 기동 시작            caddy → blue     ✔ blue 가 계속 처리
t2  green Next.js 부팅 중      caddy → blue     ✔ 여전히 blue
t3  green healthy 통과         caddy → blue     ✔ 아직 안 넘김
t4  caddy reload  ◀── 전환    caddy → green    ✔ green 은 이미 준비 완료
t5  drain 30s (blue 살려둠)    caddy → green    ✔ blue 의 잔여 요청도 완료
t6  blue stop                  caddy → green    ✔ 넘어간 지 한참 뒤
```

핵심은 **t3와 t4의 순서**입니다. healthy를 확인한 뒤에만 전환하므로, 준비 안 된 곳으로 트래픽이 가는 순간이 없습니다. 여기서 두 가지가 딸려옵니다.

- **t3에서 실패하면 전환하지 않습니다.** blue가 그대로 서비스 중이라, 빌드나 부팅이 깨진 커밋이 배포돼도 사용자는 모릅니다. 전에는 깨진 커밋이 곧 장애였습니다.
- **t6에서 `rm`하지 않고 `stop`만 합니다.** 정지된 컨테이너는 메모리를 안 쓰는데 설정과 이미지는 남아 있어서, `start` + reload로 20~30초 만에 롤백됩니다. **메모리 비용 없이 롤백 시간만 줄이는** 선택입니다.

| 방식         | 메모리          | 롤백 소요                      |
| ------------ | --------------- | ------------------------------ |
| `stop && rm` | 0               | 재생성 필요 40~60초            |
| **`stop`만** | **0**           | **`start` + reload → 20~30초** |
| 상시 실행    | 1벌분 상시 점유 | 즉시 (reload만)                |

### healthcheck가 곧 전환 조건이 된다

기존 healthcheck는 `fetch('http://localhost:3000/')`였습니다. 이게 미들웨어의 host 분기를 타서 "정말 서비스 가능한 상태"를 보장하지 않는데, blue-green에서는 **이 판정이 곧 트래픽 전환 조건**입니다. 그래서 api 도달성까지 확인하는 `/api/healthz`를 새로 두고 미들웨어 공개 경로로 등록했습니다 — 인증 게이트에 걸리면 `/login` 리다이렉트를 `fetch`가 따라가 200으로 **오판**합니다.

## 7\. 셋은 따로 놀지 않는다

세 조치는 각각 다른 문제를 풀지만, 하나만 빠져도 0이 되지 않습니다.

```plaintext
③ db·redis 제외    →  도미노를 끊는다        (없으면 admin 2벌이 무의미)
② admin 2벌        →  앱 교체 구간을 덮는다   (없으면 502 20~40초 잔존)
① caddy reload     →  전환 지점을 만든다      (없으면 전환할 방법 자체가 없음)
```

특히 ③이 없으면 앞의 둘이 통째로 헛수고가 됩니다. admin은 `API_BASE: http://api:8787`로 모든 데이터를 가져오는데, db가 죽으면 api가 죽고, api가 죽으면 **admin이 살아있어도 화면이 500**입니다. db를 건드리는 한 blue-green을 아무리 잘 만들어도 의미가 없습니다.

db·redis 강제 재생성은 없애지 않고 `workflow_dispatch` 입력으로 분리했습니다. **하루 여덟 번 자동으로 터지는 것과, 필요할 때 의도적으로 하는 것을 나눈 것**입니다.

최종 배포 흐름은 이렇게 정리됐습니다.

```plaintext
1. ACTIVE 읽기                 →  TARGET = 반대색
2. DB migrate                  →  ⚠ backward-compatible 만 (9절)
3. build + up  admin-$TARGET   →  --force-recreate --no-deps
4. healthy 대기 (최대 180s)
   └ 실패 → TARGET 정리 후 배포 실패 종료. ACTIVE 무사 = 서비스 무영향
5. active/admin.caddy 를 TARGET 으로 재작성
6. caddy validate  →  caddy reload      ◀── 트래픽 전환 지점
7. drain 30s
8. old color stop  (rm 하지 않음)
9. active/COLOR = TARGET
```

3단계에서 `--force-recreate`가 **다시 등장**하는 게 포인트입니다. 처음에 "이 플래그를 지우자"고 생각했는데 그건 부정확한 진단이었습니다. 플래그가 문제가 아니라 **대상이 없는 게** 문제였습니다. blue-green에서는 오히려 새로 띄우는 색을 강제 재생성하는 게 맞습니다 — 잔여 상태 없이 깨끗하게 뜨는 걸 보장해야 하니까요. `--no-deps`가 함께 있어야 의존성 체인을 타고 db까지 재생성되는 걸 막습니다.

## 8\. +α 디버깅 — 0이 된 줄 알았는데 12초가 남아 있었다

여기까지 하고 전환 구간을 재보니 실제로 0이었습니다. 그런데 **배포 초반에 11~14초**가 따로 남아 있었습니다.

```plaintext
16:34:11  ────────────────────────────  관측 시작
16:34:17  ✗ 랜딩·슈퍼어드민·블로그 전부 DOWN   ← 배포 시작 ~22초 후
16:34:20  ✗ 523 / 523 / 523
16:34:25  ✗ 523 / 523 / 523
16:34:31  ✓ 전부 복구                          총 11~14초
   ⋮
16:35~    ✓ 24샘플 전부 OK                     ◀── blue→green 전환 구간은 무중단
```

**코드를 한 줄도 안 바꾼 `workflow_dispatch` 배포에서 재현됐습니다.** 즉 일반 배포마다 나고 있었다는 뜻입니다. 5절에서 Caddy를 재생성 대상에서 뺐는데도요.

### 단서 1 — 이미지 ID만 바뀌었다

Caddy가 정말 재생성된 게 맞는지부터 확인했습니다.

```plaintext
생성: 2026-07-20T07:34:15Z   ← 이번 배포 중
시작: 2026-07-20T07:34:27Z
```

`생성` 시각이 배포 시각입니다. 재시작이 아니라 **재생성**이 맞았습니다. 그럼 뭐가 재생성을 트리거했을까요. 이미지를 봤습니다.

| 시점        | 이미지 ID      | CreatedAt  |
| ----------- | -------------- | ---------- |
| 배포 **전** | `a24f5a31f34d` | 2026-07-08 |
| 배포 **후** | `19dc2184f202` | 2026-07-08 |

**`CreatedAt`은 그대로인데 ID만 바뀌었습니다.** 실제로 다시 빌드된 게 아니라, 빌드 행위 자체가 새 ID를 찍어낸 겁니다. `docker compose build`가 레이어를 전부 캐시 재사용하면서도 매번 새 이미지 ID를 만들고, compose는 이미지 ID를 서비스 설정 해시에 넣습니다. 그래서 **빌드만 해도 이어지는 `up -d`가 Caddy를 재생성**합니다.

재생성 대상에서 빼놨더니, 빌드 한 줄이 우회로를 만들고 있었습니다.

### 단서 2 — 느린 건 기동이 아니라 종료였다

그래도 이상했습니다. Caddy는 설정 파싱하고 포트 바인딩하면 끝인데 왜 12초일까요. 구간을 쪼개봤습니다.

```plaintext
SIGTERM ─ caddy 가 리스너를 닫음 → 이 순간부터 521/523
   │  ◀── 약 10초: docker 가 종료를 기다림   ← 다운타임의 대부분
SIGKILL ─ 강제 종료
   │  ◀── rm + create: 1초 미만
start   ─ 설정 파싱 + 인증서 로드 + 포트 바인딩 (약 2초)
```

**기동은 2초입니다. 느린 건 종료였습니다.** Caddy 로그에 답이 있었습니다.

```plaintext
"logger":"http","msg":"servers shutting down with eternal grace period"
```

`grace_period`를 설정하지 않으면 기본값이 **무한**입니다. Caddy는 진행 중인 연결이 전부 끝나기를 기다리는데, 앞단 Cloudflare가 keep-alive 연결을 유지하고 있으니 그게 끝날 리가 없습니다. 결국 docker의 기본 종료 타임아웃 10초가 만료되어 SIGKILL됩니다. **리스너는 SIGTERM 직후에 이미 닫혔기 때문에, 그 10초는 521만 나가는 순수 대기 시간**입니다.

### 고친 것

**① Caddy는 Dockerfile이 바뀐 경우에만 빌드** (근본 원인 제거)

`Dockerfile.caddy` 내용 해시를 서버에 저장해두고 비교합니다. 무변경이면 이미지 ID가 유지되어 compose가 Caddy를 아예 건드리지 않습니다.

**② 종료를 빠르게** (재생성이 불가피할 때의 완충)

```caddy
{ grace_period 3s }
```

```yaml
caddy:
  stop_grace_period: 5s
```

11~~14초가 3~~5초가 됩니다.

## 9\. blue-green이 코드에 건 제약 — expand-contract

무중단 배포를 켜면 공짜로 얻는 것만 있는 게 아닙니다. **코드 쪽에 새 제약이 생깁니다.**

전환(t4)부터 이전 색이 정지(t6)될 때까지, 구 버전과 신 버전이 **같은 DB를 동시에** 봅니다. 그래서 모든 마이그레이션이 backward-compatible이어야 합니다.

순서 자체는 배포 스크립트가 강제합니다.

```plaintext
2. DB migrate          ◀── 여기. blue 는 아직 살아서 트래픽 처리 중
3. admin-$TARGET 기동
6. caddy reload        ◀── 여기서 트래픽 전환
```

마이그레이션이 신 코드보다 먼저 도는 건 보장됩니다. (원래는 `up -d` **뒤에** 마이그레이션이 돌고 있었습니다. 신 코드가 마이그레이션 안 된 스키마를 상대로 수십 초 도는 구조였고, 사고가 없었던 건 운에 가까웠습니다. 이번에 같이 고쳤습니다.)

진짜 제약은 **2단계 시점에 blue가 살아서 그 DB를 쓰고 있다**는 겁니다. 그래서 기준은 "머지를 나누느냐"가 아니라 **그 마이그레이션이 구 버전을 깨느냐**입니다.

| 마이그레이션                              | 배포를 나눠야 하나                                  |
| ----------------------------------------- | --------------------------------------------------- |
| nullable 컬럼·테이블·인덱스 **추가**      | ✕ 한 배포에 끝. 구 버전은 그 컬럼을 모르니 무영향   |
| 컬럼 **삭제**, `NOT NULL` 즉시, 제약 추가 | ○ **나눠야 함.** 구 버전이 아직 그 컬럼을 읽고 있음 |
| **rename**                                | ○ 3단계로 분해                                      |

파괴적 변경은 이렇게 나눠 머지합니다.

```plaintext
머지 1  새 컬럼 추가(nullable) + 백필 · 코드는 신·구 컬럼 둘 다 처리
머지 2  코드가 새 컬럼만 읽도록 전환      ◀── 이 시점에 구 컬럼 독자가 사라짐
머지 3  구 컬럼 삭제
```

**핵심은 각 배포가 그 자체로 backward-compatible이어야 한다는 것**입니다. drain 30초 동안 구/신이 겹치기 때문에, 한 배포 안에서 추가와 삭제를 같이 하면 그 30초 동안 blue가 500을 뿌립니다. 무중단 장치가 있어도 **스키마가 호환되지 않으면 다운타임은 그대로 발생합니다.**

## 10\. 결과 — 그리고 남는 3~5초

검증은 단순합니다. 배포 중에 1초 간격으로 세 도메인을 때립니다.

```bash
while :; do printf '%s %s\n' "$(date +%T)" \
  "$(curl -sS -o /dev/null -w '%{http_code}' --max-time 5 https://example.com)"; sleep 1; done
```

```plaintext
배포 시작   16:43:18
관측        16:43:32 ~ 16:45:22   (35샘플)
DOWN        0건
```

그리고 더 확실한 지표가 하나 있습니다. 배포가 끝난 시점의 `docker ps`입니다.

```plaintext
caddy   Up 4 minutes (healthy)
```

**배포가 끝난 시점에 uptime이 4분**입니다. 직전 배포에 뜬 컨테이너가 이번 배포 내내 한 번도 죽지 않았다는 뜻입니다. 재생성됐다면 `Up 20 seconds`로 찍힙니다.

| 단계                               | 배포 시 다운타임      |
| ---------------------------------- | --------------------- |
| 처음 (`--force-recreate` 전역)     | 60~100초 + 블로그 521 |
| blue-green 도입                    | 12초 (caddy 재생성)   |
| **caddy 리빌드 제거 + grace 조정** | **0초**               |

| 항목                             | 이전           | 이후                    |
| -------------------------------- | -------------- | ----------------------- |
| 블로그                           | 521 · 5~10초   | **0**                   |
| 랜딩 / 개인 어드민 / 슈퍼 어드민 | 502 · 60~100초 | **0**                   |
| 깨진 커밋 배포 시                | 장애           | **무영향** (전환 안 됨) |
| 롤백                             | 재빌드·재배포  | **설정 한 줄, 20~30초** |

### 남는 한계는 정직하게

`compose.yml`의 caddy 블록이나 `Dockerfile.caddy`, 혹은 Caddy가 쓰는 환경변수를 **실제로 바꾸는** 배포에서는 재생성이 일어나고, 그때는 3~5초가 남습니다. 해결됐다기보다 **드물어졌다**는 표현이 정확합니다.

80/443을 잡는 프로세스가 하나뿐인 한 구조적으로 남는 값입니다. 그것까지 0으로 만들려면 소켓을 넘겨받는 계층이 필요한데, 그건 규모가 다른 이야기입니다.

## 11\. 교훈

- **무중단 도구는 원래부터 있었습니다.** `caddy reload` 스텝이 워크플로에 이미 들어 있었는데, 그 앞 단계에서 Caddy를 죽여 효과를 스스로 지우고 있었습니다. 도구를 도입하는 것보다 **그 도구가 실제로 작동할 조건을 만드는 것**이 어렵습니다.

- **`--force-recreate`가 나쁜 게 아니라, 대상이 없는 게 나쁩니다.** 첫 진단은 "이 플래그를 지우자"였는데 부정확했습니다. blue-green에서는 오히려 이 플래그가 필요합니다 — 단, `--no-deps`와 함께 한 서비스에만.

- **에러 코드는 범위를 알려줍니다.** 502와 521의 차이가 "앱이 죽었나, 진입점이 죽었나"를 갈랐고, 그 한 글자가 조사 방향을 전부 결정했습니다.

- **다운타임은 재기 시작한 순간부터 줄어듭니다.** 이 글의 모든 숫자는 1초 간격 `curl` 루프 하나에서 나왔습니다. "체감상 잠깐 끊긴다"와 "11~14초, 배포 시작 22초 후"는 완전히 다른 정보입니다.

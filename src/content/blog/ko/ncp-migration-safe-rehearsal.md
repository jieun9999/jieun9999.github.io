## 들어가며

데이터 이전 방식을 결정한 뒤, 실제 전환 전에 운영 데이터로 리허설했다. 목표는 복사 성공 여부만 확인하는 것이 아니라 **점검 시간을 측정하고, 전환 당일 처음 겪을 문제를 미리 찾아 해결하는 것**이었다.

[2편](/ko/blog/ncp-account-migration-strategy/)에서는 PostgreSQL·Redis를 **덤프·복원하고 잠깐 쓰기를 멈추는 방식**을 선택했다. 당시 예상한 점검 시간은 15–20분이었다. 하지만 복원에 걸리는 시간만 안다고 전체 중단 시간을 예측할 수는 없었다. 새 앱을 띄우고, DB 연결과 채팅·파일 기능을 확인한 뒤 트래픽을 바꾸는 데도 시간이 필요했다.

더 큰 걱정은 **전환 당일에 예상하지 못한 오류를 처음 만나는 것**이었다. PostgreSQL 확장 때문에 복원이 멈추거나 새 앱이 기존 메시지 서버로 요청을 보내면, 사용자가 서비스를 이용하지 못하는 동안 원인을 찾아야 한다. 데이터가 제대로 옮겨지더라도 설정 하나가 잘못돼 있으면 전환을 끝낼 수 없다.

그래서 실제 운영 데이터로 최종 전환과 같은 순서를 미리 실행했다. 확인할 것은 세 가지였다. **데이터와 기능이 정상인지, 전환에 얼마가 걸리는지, 당일 작업을 막을 문제는 없는지.**

다만 검증 과정 자체가 장애가 되어서는 안 됐다. 복원된 DB에는 실제 사용자 정보가 있고, 복사한 설정에는 푸시·메일·파일 저장소에 접근하는 비밀값도 포함돼 있었다. 새 환경에서 테스트한 내용이 운영 사용자에게 전달되지 않도록, **운영 DB에 대한 변경을 차단하고 리허설용 앱의 접근 범위도 제한했다.**

## 1. 운영 DB는 한 번 읽고, 이후에는 복제본으로 시험했다

먼저 자동 백업이 정상인지 확인했다. 운영 DB는 읽기 전용으로 한 번 덤프하고, 이후 복원과 테스트는 그 파일을 이용했다. 운영 DB에 반복해서 접속하거나 스키마를 수정할 필요가 없었다.

![운영 DB를 읽기 전용으로 덤프한 뒤 같은 파일을 로컬과 새 계정에 복원하는 경로](/images/ncp-migration/rehearsal-isolation.svg "diagram")

기존·새 계정 사이에는 VPC Peering을 연결하지 않았다. 관리형 DB는 NKS 노드 대역에서만 접근할 수 있어, 덤프와 복원을 각각 **클러스터 안의 임시 파드**에서 실행하고 `kubectl cp`로 파일을 옮겼다. 운영자 PC는 중간 파일과 검증 결과를 확인하는 역할을 맡았다. 데이터 규모가 작았기 때문에 계정 간 상시 연결을 만드는 것보다 이 구조가 간단했다.

운영 DB에서 받은 파일은 먼저 로컬 Docker DB에 복원해 확인했다. 이 컨테이너의 네트워크를 차단해 다른 환경으로 연결되지 않도록 했고, 같은 파일을 새 계정 DB에도 복원했다. **반복 시험 중 오류가 나도 운영 DB를 다시 건드리지 않는 것**이 이 순서의 목적이었다.

실수를 막기 위한 검사도 스크립트에 넣었다. 원본 클러스터를 복원 대상으로 지정할 수 없게 하고, Kubernetes API 서버 주소와 PostgreSQL 서버 식별자, Redis `run_id`를 비교해 원본과 대상이 같은지 확인했다. 클러스터별 kubeconfig 파일도 분리했다. 새 환경의 설정이 잘못되더라도 운영 DB에 직접 닿을 네트워크 경로는 없었다.

## 2. 복사 명령이 성공해도 데이터가 맞는지는 따로 확인했다

PostgreSQL 접속 정보는 명령어에 쓰지 않고 Kubernetes Secret으로 임시 파드에 전달했다. 원본 세션에는 읽기 전용 옵션을 적용했다.

```bash
PGOPTIONS='-c default_transaction_read_only=on'
```

덤프는 `pg_dump -Fc`로 만들었다. 관리형 DB의 앱 계정은 확장 설치 권한이 없으므로, 확장은 대상 DB에 미리 준비하고 덤프 목차에서 해당 설치 항목을 제외했다. 기존 DB의 소유자·권한 정보도 새 계정에 그대로 적용하지 않았다. 복원은 `pg_restore -1 --exit-on-error`로 한 트랜잭션에서 실행해 중간 실패 시 일부만 반영되지 않도록 했다.

완료 여부는 종료 코드로만 판단하지 않았다. **원본과 새 DB의 테이블 목록과 각 테이블의 정확한 행 수를 비교**했고, 차이가 있으면 다음 단계로 넘어가지 않게 했다. 리허설에서는 285개 테이블이 일치했다. 데이터 양이 50만 행 안팎이라 통계상의 추정 행 수보다 실제 `count(*)`로 검증하는 비용이 감당할 만했다.

물론 행 수가 같다고 모든 레코드 내용이 동일하다고 증명되는 것은 아니다. 그래서 같은 덤프를 복원하고, 복원 중 오류가 있으면 즉시 중단하며, 테이블 수·행 수를 대조하는 여러 검증을 함께 사용했다. **어느 한 단계의 성공 메시지에 의존하지 않게** 만든 것이다.

Redis 역시 일부 세션만 골라 옮기지 않았다. 로그인 정보 외에 사용량 통계처럼 Redis에만 있는 데이터가 있었기 때문이다. 같은 Redis 버전에서 `DUMP`·`RESTORE`를 사용하고 `PTTL`로 남은 만료 시간도 함께 옮겼다. 그다음 키 수를 대조했다.

## 3. 새 앱의 요청이 운영 환경으로 나가지 않는지 확인했다

새 환경을 공개하기 전에 운영자 맥북의 `/etc/hosts`만 수정했다. 그 PC에서만 새 로드밸런서로 접속하고, 실제 사용자들의 요청은 기존 NKS로 계속 향하게 했다. 운영팀 계정과 개인 시험 계정만 사용하고, 두 계정만 있는 대화방에서 로그인·채팅·파일 업로드·관리자 기능을 확인했다.

파일 저장소처럼 환경변수에 복사된 외부 서비스는 여전히 실제 운영 자원을 가리킬 수 있었다. 따라서 테스트용 파일과 계정을 제한하고, 확인 후 파일을 정리했다. **DNS를 바꾸지 않는 것만으로 모든 외부 영향이 사라지는 건 아니었다.**

worker는 더 조심해야 했다. 웹 앱과 달리 실행 직후 Redis에 쌓인 예약 작업을 처리할 수 있어서다. 운영 데이터와 같은 Secret을 가진 worker가 푸시나 메일을 중복 발송하지 않도록 **Cilium NetworkPolicy로 외부 통신을 막고**, 새 DB·Redis 등 시험에 필요한 내부 통신만 허용했다. 정책이 실제로 외부 요청을 차단하는지 확인한 뒤 worker를 실행했다.

정책을 적용했다는 이유만으로 격리가 됐다고 가정하지 않았다. worker 기동 전에 파드에서 실제 외부 통신이 차단되는지 확인하고, 그다음 앱이 내부 DB와 Redis를 정상적으로 사용하는지 살펴봤다.

리허설에서는 worker를 **19분 동안 실행해 13개 큐의 약 650건을 처리**했고, DB·Redis 오류는 없었다. 다만 외부 호출을 차단했으므로 이 결과만으로 푸시나 메일 발송 성공을 증명할 수는 없었다. **리허설에서 확인할 수 있는 범위와 실제 운영 전환 후 확인해야 할 범위**를 구분했다.

## 4. 리허설에서 실제로 발견한 문제

리허설을 진행하면서 예상하지 못한 문제가 세 가지 나왔다. 모두 겉으로는 정상처럼 보이거나, 명령의 성공 여부만 보면 지나치기 쉬운 문제였다. 각각의 문제가 **어떤 시험에서 드러났고, 전환 전에 무엇을 수정했는지** 정리했다.

### 4-1. 새 웹에서 보낸 메시지가 기존 Centrifugo로 전달됐다

새 계정의 웹에 접속해 채팅을 시험했는데, 메시지가 새 클러스터가 아니라 **기존 운영 Centrifugo로 발행되고 있었다.** 복사해 둔 `CENTRIFUGO_API_URL`이 기존 서비스의 공개 주소를 가리키고 있었기 때문이다.

![리허설에서 발견한 기존 운영 Centrifugo 연결과 새 클러스터 내부 주소로 수정한 경로](/images/ncp-migration/centrifugo-routing.svg "diagram")

새 웹은 정상으로 뜨고 로그인도 가능했다. 하지만 실시간 메시지는 웹 서버에서 별도의 Centrifugo API로 발행된다. 웹의 접속 주소만 새 환경으로 바꿔서는 메시지가 어느 실시간 서버로 가는지 알 수 없었다. 이 경로를 따로 확인하면서 설정값이 잘못 복사됐다는 사실을 발견했다.

이대로 전환했다면 웹과 DB는 새 계정을 사용하면서 메시지 발행은 기존 계정으로 보내는 구성이 된다. 새 클러스터 내부의 실시간 연결과 실제 메시지 경로가 일치하지 않아, 채팅 지연이나 전달 오류를 전환 당일에 조사해야 했을 것이다.

설정을 새 클러스터의 **내부 Centrifugo 주소**로 바꿨다. 실제 전환 당일에도 메시지가 즉시 표시되는지 확인했다. 이 문제로 리허설 체크리스트에 추가된 기준은 단순했다. **서비스가 실행 중인지만 보지 말고, 내부 의존 서비스의 실제 접속 대상까지 확인한다.**

### 4-2. PostgreSQL 확장 스키마 때문에 첫 복원이 실패했다

PostgreSQL도 첫 시도에서 복원이 실패했다. `vector`, `pg_stat_statements` 확장이 예상한 스키마가 아니라 NCP 관리형 DB의 `cdb_admin` 스키마에 설치돼 있었다. 확장을 대상 DB에 미리 준비하는 것만으로는 복원 과정의 스키마 차이를 해결할 수 없었다.

초기 스크립트는 확장 설치 문장을 제외한 나머지 복원이 정상적으로 진행될 것이라고 가정했다. 하지만 관리형 PostgreSQL에서는 확장을 설치할 수 있는 계정과 스키마가 일반적인 환경과 다를 수 있다. 같은 메이저 버전의 PostgreSQL을 준비했다고 해도 관리형 서비스의 내부 구성이 완전히 같다는 뜻은 아니었다.

기존 복원 runner를 수정해 **덤프 파일에서 확장의 스키마 정보를 읽고** 그에 맞게 처리하도록 했다. 수정 후 다시 복원해 285개 테이블의 행 수가 일치하는지 확인했다. 단순히 오류가 사라졌는지만 본 것이 아니라, 원래 검증 기준을 다시 통과하는지 확인한 것이다.

운영 전환 중에 같은 오류를 처음 만났다면, 쓰기를 멈춘 상태에서 원인을 조사하고 복원을 재시도해야 했을 것이다. 이전 전용 스크립트를 작성할 때는 문법이나 옵션뿐 아니라 **복원 대상의 관리형 DB 특성도 실제 덤프로 시험해야 한다**는 점을 확인했다.

### 4-3. Redis를 덮어쓴 뒤에도 이전 리허설의 키 699개가 남았다

Redis 복사에서는 명령이 성공했는데도 원본과 대상의 키 수가 맞지 않았다. `redis-import --replace`는 같은 이름의 키를 덮어쓰지만, **대상에만 있는 키를 삭제하지는 않는다.** 이전 리허설에서 생긴 키 699개가 그대로 남아 있었다.

원인은 복사의 의미를 다르게 이해했던 데 있었다. `replace`는 충돌하는 키를 교체한다는 뜻이지, 대상 Redis 전체를 원본과 동일한 상태로 만든다는 뜻은 아니다. 리허설을 여러 번 하면서 대상에 남은 키가 그대로 쌓일 수 있었다. 명령이 오류 없이 끝났다는 이유만으로 데이터가 같다고 판단했다면 발견하기 어려웠다.

Redis에는 캐시뿐 아니라 로그인 세션, 모바일 세션 포인터, 사용량 통계처럼 복원 시점의 상태를 정확히 맞춰야 하는 데이터도 있었다. 데이터 복사를 마친 뒤 키 수를 대조하는 검증을 별도로 넣었기 때문에 차이를 확인할 수 있었다.

이 문제는 리허설에서 발견했지만, **복사 도구를 완전히 고친 시점은 운영 전환 이후**였다. 전환 당일에는 잔여 키를 수동으로 대조·정리해 최종적으로 **9,587개 키가 일치**하는 것을 확인했다. 이후 runner를 '기존 키를 덮어쓰기'가 아니라 **'대상을 비우고 복원하기'** 방식으로 수정했다.

이번 사례에서는 발견·임시 대응·도구의 영구 수정이 한 번에 끝나지 않았다. 따라서 리허설에서 문제를 발견했다고 해서 모든 수정을 사전에 자동화한 것처럼 쓰지 않는 게 중요했다. **전환 당일의 수동 검증과 사후 도구 개선**이 각각 다른 역할을 했다.

세 문제는 원인이 달랐다. 환경변수에 남은 기존 서비스 주소, 관리형 PostgreSQL의 확장 스키마, Redis의 `replace` 동작에 대한 가정이었다. 하지만 모두 **성공 조건을 명확히 검증하지 않았다면 놓쳤을 문제**였다.

이 리허설에서 확인한 것은 "데이터 복사를 실행할 수 있다"는 사실보다 더 구체적이었다. **새 웹이 새 실시간 서버를 사용하는가, 관리형 DB에서 복원과 행 수 대조가 끝까지 통과하는가, Redis에 원본에 없는 키가 남아 있지 않은가.** 전환 당일의 검증 항목도 이 질문들에 맞춰 보강했다.

## 5. 10월 23일 실제 전환 결과

리허설을 마친 뒤 새 앱은 대기 상태로 되돌렸다. 실제 전환에서는 10월 22일 23시 59분에 기존 서비스의 쓰기를 멈추고, 23일 00시 1–5분에 PostgreSQL과 Redis를 최종 복사했다. 00시 6분 새 앱을 기동한 뒤 00시 12분 Cloudflare 진입점을 전환했다.

| 검증 항목 | 결과 |
| --- | --- |
| PostgreSQL | **285개 테이블, 495,192행 일치** |
| Redis | **9,587개 키 일치** |
| 사용자 영향 | **약 13분** |
| 전환 후 1시간 웹 요청 | **5,518건, 5xx 0건** |
| 같은 기간 worker 작업 | **1,926건 성공, 재시작 0회** |

웹·데스크톱·모바일의 로그인 유지와 실시간 채팅·파일·푸시도 확인했다. 사전 리허설에서 측정한 데이터 이동 시간은 약 2분이었지만, 실제 전환에는 앱 중지·기동과 기능 확인이 포함됐기 때문에 총 영향 시간은 더 길었다.

중요한 것은 **13분이라는 수치만이 아니었다.** 원본과 대상의 데이터를 비교할 기준이 있었고, 문제가 발생하면 어떤 단계에서 멈출지 미리 결정해 두었다. 실제로 전환을 마친 뒤에는 별도의 배포 경로 검증과 모니터링 점검이 이어졌다.

## 마무리하며

이번 리허설의 목적은 복사가 성공한다는 사실을 한 번 확인하는 데 있지 않았다. **잘못된 클러스터로 복원하지 않도록 막고, 복제한 앱이 운영 환경을 건드리지 않게 격리하고, 최종 전환 전에 예상하지 못한 연결과 데이터 차이를 찾는 것**이 중요했다.

실제로 PostgreSQL 확장 스키마, Centrifugo 주소, Redis 잔여 키 문제를 발견했다. 점검 시간에 처음 만났다면 전환이 길어지거나 데이터를 다시 대조해야 했을 문제들이다. 2편에서 선택한 단순한 이전 방식이 안전하게 작동할 수 있었던 건, 그 단순함을 전제로 **반복 가능한 검증 절차를 마련했기 때문**이었다.

## 들어가며

Terraform과 NKS로 새 운영 환경을 준비한 뒤에도 남은 문제가 있었다. PostgreSQL과 Redis의 데이터를 어떻게 옮길 것인가. 무중단 전환이 가능한지부터 검토했지만, 결국 짧은 점검 시간을 확보해 데이터를 한 번에 옮기는 방식을 선택했다. 이 글은 그 판단의 근거를 정리한 기록이다.

[1편](/ko/blog/ncp-account-migration-terraform-nks/)에서는 NCP 계정을 옮기면서 인프라와 배포 환경을 다시 구성한 과정을 다뤘다. 서버는 새로 만들 수 있지만, 운영 중인 데이터는 그렇지 않았다. 메시지와 근태·결재 기록은 PostgreSQL에, 로그인 세션과 사용량 정보 일부는 Redis에 남아 있었다.

이전 작업을 인수받기 전, 로그인 서비스를 새 계정으로 전환했다가 되돌리는 과정에서 **며칠간의 로그인·감사 기록이 운영 DB에서 빠진 사례**도 있었다. 중요한 계정 정보의 변경은 없었고 원본 백업도 보존돼 있었지만, 트래픽을 되돌린다고 데이터까지 원래대로 돌아오는 것은 아니라는 점이 분명해졌다.

이전 담당자가 남긴 계획에는 PostgreSQL 논리 복제도 있었다. 복제는 중단을 줄이는 데 유리하지만, 운영 중인 DB에 연결과 복제 상태를 새로 도입해야 한다. 당시에는 인프라를 인수받은 지 얼마 되지 않았고, 먼저 운영 중인 구성 자체를 확인해야 하는 상황이었다.

그래서 질문을 바꿨다. *어떻게든 무중단으로 옮길 수 있을까?* 보다 **어느 시점에 쓰기를 멈추고, 어떤 조건에서 전환해야 데이터가 갈라지지 않을까?** 가 먼저였다.

## 1. 앱만 바꾸는 블루그린 배포와는 다른 문제였다

일반적인 블루그린 배포에서는 두 앱이 같은 DB를 사용할 수 있다. 하지만 이번에는 앱뿐 아니라 DB 자체도 다른 NCP 계정으로 옮겨야 했다.

```text
기존 앱 → 기존 DB
새 앱   → 새 DB
```

두 환경에서 동시에 쓰기를 받으면 사용자의 기록이 서로 다른 DB에 쌓인다. 이후 이전 계정으로 돌아가더라도 새 DB에 생긴 기록을 따로 처리해야 한다. 반대로 한쪽 DB에만 쓰도록 제어한다면 앱을 두 곳에 띄우는 것 자체는 가능하지만, 결국 데이터 저장소가 바뀌는 순간에는 동기화와 쓰기 제어가 필요하다.

실제 로그인 서비스의 데이터 공백 사례를 겪었기 때문에, **두 DB가 각자 쓰기를 받는 구간을 만들지 않는 것**을 전환의 원칙으로 삼았다. 단순히 접속 경로가 정상인지보다, *새 계정에서 발생한 쓰기를 이전 계정으로 되돌릴 수 있는가*가 더 중요한 질문이었다.

## 2. 세 가지 이전 방식을 비교했다

| 방식 | 얻을 수 있는 것 | 이번 환경에서 추가되는 부담 |
| --- | --- | --- |
| **덤프·복원 후 전환** | 절차가 단순하고 전환 지점이 명확하다 | 최종 데이터 복사 중 서비스 쓰기를 멈춰야 한다 |
| **논리 복제 후 전환** | 쓰기 중지 시간을 더 줄일 수 있다 | 계정 간 SSH 터널, 복제 슬롯, 시퀀스 동기화, DDL 동결과 복제 상태 관리가 필요하다 |
| **앱 먼저 전환, DB는 나중에 이전** | 앱 전환 자체는 중단 없이 할 수 있다 | 새 앱이 기존 DB·Redis에 접근할 네트워크가 필요하고, DB 이전을 위해 다시 전환해야 한다 |

**논리 복제**는 중단을 줄이는 데 가장 직접적인 방법이었다. 먼저 전체 데이터를 동기화하고 운영 DB의 변경분을 계속 따라가게 하면, 전환 당일에는 마지막 차이만 확인하면 된다. 이전 기록에도 실제 테이블을 동기화한 흔적이 있었다.

하지만 테이블 내용이 따라간다는 것만으로 이전이 끝나지는 않는다. 시퀀스와 DDL 변경은 별도로 다뤄야 하고, 복제 연결·슬롯·지연 상태를 계속 관찰해야 한다. 복제 슬롯을 정리하지 않으면 WAL 보관량이 늘어날 수도 있다. 이전이 끝나면 없앨 연결 구조를 당장 도입해야 하는 만큼, **줄어드는 점검 시간과 추가되는 실패 지점**을 함께 비교했다.

**앱을 먼저 옮기고 DB를 나중에 이전하는 방법**도 검토했다. 새 앱이 기존 DB를 공유하면 첫 번째 트래픽 전환 자체는 무중단에 가까울 수 있다. 다만 두 계정 사이의 네트워크 연결을 추가하고, DB·Redis 접속 허용 범위를 넓혀야 했다. 데이터 저장소를 옮기는 시점에는 또 다른 전환이 필요했다.

이 방식은 앱 변경 폭이 크거나 DB 데이터가 매우 커서 작업을 나눠야 할 때 유리하다. 이번에는 같은 앱 이미지를 옮기는 작업이었고, 데이터도 작았다. **앱 전환이 무중단이라는 것과 계정 이전 전체가 무중단이라는 것은 달랐다.**

## 3. 실제 데이터 규모와 이용 시간을 기준으로 결정했다

판단에 사용한 수치는 다음과 같았다.

| 확인한 항목 | 당시 측정값 |
| --- | --- |
| PostgreSQL 실데이터 | 약 623MB |
| PostgreSQL 덤프 파일 | 46.5MB |
| DB 복원 | 43초, 285개 테이블 일치 *(10월 7일의 사전 시험 기록)* |
| Redis | 약 9천 개 키 |
| 새벽 03–08시 메시지 | 시간당 0–18건 *(이전 4주 기준)* |

데이터 복사 자체보다 앱을 멈추고 다시 띄우는 시간, 새 환경에서 기능을 확인하는 시간이 더 클 가능성이 높았다. 서비스에는 이미 점검 모드가 있었고, Cloudflare 프록시의 원본 주소를 변경해 새 로드밸런서로 트래픽을 보낼 수 있었다. 이전 4주간의 메시지 수를 확인한 것도 이 때문이다. 막연히 "새벽에는 이용자가 없겠지"라고 가정하지 않고, 실제로 어떤 시간대가 상대적으로 조용한지 확인했다.

당시 계획상 덤프 방식의 쓰기 정지 시간은 약 15–20분, 논리 복제 방식은 약 3–5분으로 예상했다. 이는 **방식을 선택할 때의 추정치**다. 논리 복제를 택하더라도 앱 재기동·Redis 이전·기능 확인 시간이 사라지는 것은 아니었다. 따라서 차이가 나는 것은 전체 점검 시간 중 일부였다.

결국 **새 환경을 미리 구성하고 검증한 다음, 점검 시간에 최종 데이터만 옮기기로 했다.** PostgreSQL도 계정 이전과 동시에 17로 업그레이드하지 않고 기존과 같은 15.15를 유지했다. 이전 범위가 늘어날수록 원인을 파악해야 할 변수가 많아지기 때문이다.

Redis는 처음에 로그인 토큰만 가져오려 했지만, 운영 키를 분류해 보고 전체를 옮기기로 했다. 캐시처럼 다른 원본에서 다시 만들 수 있는 데이터가 있는 반면, **아직 DB로 옮겨지지 않은 사용량 통계**와 모바일 로그인 상태처럼 Redis에만 남은 정보도 있었다. 무엇을 버려도 되는지 하나씩 판단하는 과정이 오히려 누락 위험을 만들었다.

또한 PostgreSQL에서 어떤 방식을 선택하든 Redis의 상태 이전은 따로 필요했다. 그 때문에 논리 복제로 PostgreSQL의 쓰기 정지 시간을 줄이더라도 전체 서비스 전환이 자동으로 무중단이 되는 것은 아니었다. 약 9천 키라면 전체 복사가 충분히 가능한 규모라고 판단했다.

## 4. 중단보다 중요했던 것은 쓰기 재개 시점이었다

최종 절차는 간단하게 정리했다.

![최종 데이터 대조와 새 앱 확인을 통과한 뒤 쓰기를 재개하는 전환 절차](/images/ncp-migration/cutover-gates.svg "diagram")

이 순서에서 중요한 것은 점검 화면을 켜는 것과 실제 쓰기 중지를 혼동하지 않는 일이었다. 외부 요청을 막아도 내부 worker나 예약 작업이 DB에 계속 기록할 수 있다면 최종 덤프 이후에도 원본 데이터가 바뀔 수 있기 때문이다. 따라서 앱과 작업을 멈춘 뒤 최종 데이터를 복사하는 순서를 택했다.

새 환경에서 사용자 쓰기가 시작되기 전까지는 기존 환경으로 돌아갈 여지가 있다. 반면 **전환 후 새 DB에 기록이 쌓였다면 DNS만 되돌리는 것으로는 복구할 수 없다.** 이미 발생한 쓰기를 어떻게 다룰지 별도의 판단이 필요하다. 그래서 단순히 주소를 바꾸는 순간이 아니라, 데이터 대조와 새 서비스 확인을 통과한 뒤 쓰기를 재개하는 시점을 기준으로 절차를 설계했다.

처음 계획에서 점검을 1–2시간으로 예상했던 이유에는 새 환경 확인까지 전환 당일에 포함돼 있었기 때문이다. 이 작업들을 전날 리허설로 옮기면, 당일에는 **쓰기 중지·최종 데이터 복사·검증·트래픽 전환**에만 집중할 수 있다.

실제 이전은 10월 23일에 약 13분의 사용자 영향으로 마쳤다. 선택 당시 예상했던 점검 범위 안이었다.

## 마무리하며

무중단이 언제나 더 안전한 것은 아니다. 이번처럼 데이터 규모가 작고 짧은 점검을 허용할 수 있는 환경에서는, 몇 분을 더 줄이기 위해 임시 네트워크와 복제 상태를 관리하는 편이 오히려 부담이 컸다.

핵심은 덤프가 논리 복제보다 낫다는 결론이 아니다. **서비스 규모와 운영 조건을 먼저 측정하고, 그 조건에 맞는 복잡도를 선택했다는 점**이다.

방식을 정한 다음에는 실제 운영 데이터로 복원과 앱 동작을 확인해야 했다. [3편](/ko/blog/ncp-migration-safe-rehearsal/)에서는 이 결정을 어떻게 구현하고, 운영 환경에 영향을 주지 않으면서 어떤 문제를 발견했는지 다룬다.

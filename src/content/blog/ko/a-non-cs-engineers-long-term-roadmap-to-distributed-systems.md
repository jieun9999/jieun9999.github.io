> 나는 지금까지 너무 **1~2년 단위의 단기 성과**에만 집중해온 것 같다. 그래서 더 멀리, 더 깊게 보지 못했고, 개발자로서의 나 자신에 장기적으로 투자하는 걸 계획하지 못했다. 단기적 시각이 오히려 **기회를 축소**시키고 있었다.

이 글은 그 자각에서 출발한 브레인스토밍의 전체 기록이다. 비전공·부트캠프 출신, 경력 1년이 채 안 된 주니어가 "어떻게 하면 장기적으로 준비하며 글로벌 서비스 회사까지 가볼 수 있을까"를 붙들고 정리한 서사다. 결론부터 말하면, 답은 화려한 점프가 아니라 **조용한 복리**였다.

## 1. 현인들의 지혜 — 복리, 그리고 중단하지 않기

### 워렌 버핏 — 복리(Compounding)

> "누군가 오늘 그늘에 앉아 쉴 수 있는 건, 오래전에 누군가 나무를 심었기 때문이다."

버핏의 본질은 사실 투자가 아니라 **복리적 사고**다. 그는 하루 500페이지씩 읽으며 "지식은 복리처럼 쌓인다"고 했다. 실력은 선형이 아니라 지수함수다. 1년 차와 8년 차의 차이는 "8배 경험"이 아니라 **복리로 벌어진 격차**다.

### 찰리 멍거 — 매일 조금씩 더 현명해지기

> "매일 잠들기 전에, 아침에 일어났을 때보다 조금 더 현명해지려고 노력하라. 그렇게 오래 살아남으면, 대부분의 사람들은 도달하지 못하는 곳에 도착한다."

핵심은 **"오래 살아남으면"** — 꾸준함 × 시간이다. 화려한 도약이 아니라 매일의 미분값.

### 찰리 멍거 — 복리의 제1원칙

> "복리의 첫 번째 규칙: 불필요하게 중단하지 마라."

1~2년마다 방향을 바꾸면 복리가 **리셋**된다. 단기 성과 압박이 바로 이 중단이다.

### 나발 라비칸트 — 개발자를 위한 현대의 현인

> "장기적인 사람들과 장기적인 게임을 하라." / "부는 잠자는 동안에도 돈을 버는 자산이다. 시간을 팔지 말고 지렛대(leverage)를 만들어라."

개발자에게 **코드는 잠자는 동안에도 일하는 지렛대**다. 그리고 "진정성으로 경쟁을 탈출하라"는 말은, 남들과 똑같은 스택으로 경쟁에 매몰되지 말라는 뜻이다.

```
  단기 성과 압박 ──▶ 시야 축소 ──┐
   (1~2년 단위)                  ├──▶ 기회 축소 ──┐
             └──▶ 복리 중단 ─────┘                │
                                                  ▼
                                   [자각] 장기 시각으로 재설계
```

## 2. 멍거의 역발상 — "어떻게 하면 절대 못 갈까?"

멍거는 늘 말한다. **"뒤집어라, 항상 뒤집어라(Invert, always invert)."** "어떻게 탑티어에 갈까?"가 아니라 **"어떻게 하면 절대 못 갈까?"** 를 먼저 물으면 로드맵이 저절로 나온다.

```
  ❌ CRUD만 반복             →  ✅ 매 프로젝트에서 새로운 난이도
  ❌ 트래픽/스케일 무경험     →  ✅ 스스로 스케일 경험을 만든다
  ❌ 원리(CS 기초) 없이 조립  →  ✅ CS 기초를 밑바닥부터
  ❌ 영어를 미룸             →  ✅ 매일 30분, 3년이면 원어민 면접
```

특히 "트래픽 없는 회사"는 많은 주니어의 약점이다. 회사가 스케일 경험을 안 주면, **스스로 만들면 된다.** 오픈소스 기여, 개인 프로젝트 실배포 + 부하테스트 + 모니터링 + 장애대응. 이게 트래픽 회사 출신과 겨룰 수 있는 유일한 길이다.

> [!NOTE]
> **인생의 안전망은 장기적 사고를 가능케 한다.** 약간의 재정적 활주로가 있다면, 그건 "단기 성과 압박에서 벗어날 자유"이자 "연봉을 조금 손해 보더라도 더 많이 배우는 회사로 갈 선택지(optionality)"를 사는 자원이다. 그리고 인생의 장기 파트너십(가족 등)은 나발이 말한 "장기적인 사람과의 장기 게임" 그 자체다.

## 3. 증명서(Certificate)가 아니라 증거(Evidence)

여기서 가장 중요한 관점 전환이 나온다.

> **탑티어 회사는 "CS를 공부했다는 증명서"를 거의 안 본다.** 온라인 수료증, 나노디그리는 시니어 면접관에게 가산점이 되지 않는다.

그들에게 통용되는 유일한 "증명"은 두 가지다.

1. **그들의 면접을 통과하는 것** (CS 지식의 실시간 증명)
2. **공개된 결과물** — 증명서가 아니라 *증거*

```
  증명서(Certificate)  "믿어주세요"   ──▷  신뢰 낮음
  증거(Evidence)       "직접 보세요"  ══▶  신뢰 높음
```

즉, 만들어야 할 것은 certificate가 아니라 **evidence**다. 증명서는 "믿어주세요"고, 증거는 "직접 보세요"다.

### 신호 강도의 위계

무엇이 실제로 탑티어 엔지니어를 설득하는가, 강한 순서로:

```
  ★★★★★  직접 만든 것 (밑바닥부터 구현)
           Redis 자료구조 / SQLite 클론 / 미니 셸 / TCP 구현
           ⭐ MIT 6.824 Raft 구현  ← 최고의 무기
  ★★★★☆  기술 블로그 (이해의 증거 + 사고력)  "잠자는 동안 일하는 지렛대"
  ★★★★☆  오픈소스 기여 (Merged PR = 반박 불가능한 도장)
  ★★★☆☆  Codeforces 레이팅 (통용되는 숫자 증명서)
  ★★☆☆☆  수료증 (커리큘럼 가이드로만 의미. 예외: 정식 온라인 석사)
```

> **실전 전략: "GitHub + 블로그"를 당신의 학위증으로 만들어라.** 이력서엔 수료증 대신 링크를 건다:
> `Implemented Raft consensus (MIT 6.824) — [github link]`

## 4. "Raft 한 줄"의 정체

위 한 줄을 단어별로 해부해보자.

**`Raft` = 합의 알고리즘(Consensus Algorithm).** 서버 한 대는 죽으면 끝이다. 그래서 데이터를 여러 대에 복제한다. 그런데 "네트워크가 끊기고 몇 대가 죽어도 **모두가 같은 데이터에 동의**하게 만들려면?"이라는 난제가 생긴다. Raft는 이걸 푸는, 가장 유명하고 이해하기 쉬운 알고리즘이다(원래 Paxos가 너무 어려워서 "이해 가능한 합의"를 목표로 만들어졌다). Raft가 다루는 것:

- **리더 선출(Leader election)** — 대장을 뽑고, 죽으면 재선출
- **로그 복제(Log replication)** — 대장의 명령을 나머지에 복사
- **안전성(Safety)** — 장애가 나도 데이터가 꼬이지 않게 보장

이건 장난감 지식이 아니라 **etcd(쿠버네티스 핵심), Consul, TiDB, CockroachDB**의 심장부에서 돌아가는 실전 기술이다.

**`(MIT 6.824)` = MIT 분산시스템 대학원 수업**(현 6.5840). 강의·자료·과제가 전부 무료 공개돼 있고, 유명한 과제가 "Raft를 Go로 밑바닥부터 구현"이다(악명 높게 어렵다). 이 괄호는 "아무 Raft가 아니라 그 6.824 과제를 완주했다"는 신뢰의 출처다.

**`— [github link]` = 증거의 링크.** 주장이 아니라 실제 통과한 코드를 클릭 한 번으로 확인시킨다.

> 전체 의미: *"MIT 분산시스템 수업의 그 어려운 Raft 과제를 직접 구현해 통과시켰고, 코드가 GitHub에 있으니 직접 확인하라."* — 트래픽 없는 회사의 주니어가 이 한 줄을 넣으면, **"실전 트래픽은 부족해도 분산시스템의 근본을 스스로 파고드는 사람"** 이라는 강력한 신호가 된다.

## 5. 반전 — 나는 이미 분산시스템을 하고 있었다

그런데 내 블로그의 지난 글들을 냉정하게 다시 봤더니, 놀라운 사실을 발견했다. **주제 하나하나가 이미 분산시스템이었다.** 단지 이름을 안 붙였을 뿐.

| 지난 글 | 사실 이건 이 분야였다 |
|---------|----------------------|

| [크래시 복원 녹음 파이프라인 — savepoint, 상태머신](/ko/blog/building-a-crash-resilient-end-to-end-meeting-recording-pipeline-in-the-browser/) | **내구성 / 크래시 복구(WAL·checkpointing)** |
| [KeyDB→Valkey Sentinel HA 마이그레이션](/ko/blog/why-you-should-never-use-keydb-as-a-pub-sub-broker-for-centrifugo/) | **복제 & 리더 선출 = Raft가 푸는 문제** |
| [프로덕션 QPS 10배 스케일링](/ko/blog/scaling-qps-10x-in-production-3-strategies-that-actually-move-the-needle/) | **성능 엔지니어링** |

```
  내가 실무로 한 것                사실은 이 CS 개념
  ─────────────────               ─────────────────
  5분마다 flush(savepoint)   ─▶   체크포인팅 / WAL
  BullMQ delayed job 상태머신 ─▶  분산 작업 스케줄링 + 크래시 복구
  Sentinel HA failover      ─▶   복제 & 리더 선출  (= Raft!)
  데드락을 찾아 수정          ─▶   동시성 이론
```

> [!IMPORTANT]
> **결론이 뒤집힌다.** 나는 "분산시스템에서 멀리 있는 초보자"가 아니라, **분산시스템을 경험적(empirical)으로는 이미 하고 있는데, 그 밑에 깔린 이론(theory)이 비어 있는 사람**이었다. 이건 6.824에 **가장 이상적인 후보**다. 6.824가 어려운 이유는 개념이 낯설어서인데, 나는 그 개념들을 이미 현장에서 만졌기 때문이다.

없는 것은 딱 세 가지였다: **① Go 언어 ② 동시성의 형식적 기초 ③ 논문 읽는 근육.**

## 6. 그런데 CS 기초를 먼저 채워야 하지 않을까?

여기서 정당한 의문이 든다. "나는 학부 CS를 안 들었는데, 기초부터 체계적으로 채워야 하지 않나?" 부분적으로 맞다. 두 가지 학습 철학이 있다.

- **① Bottom-up(학사 순서):** 자료구조→구조→OS→네트워크→분산시스템. 완전하지만 느리고, 동기가 없으면 지친다. 그리고 이미 아는 걸 반복한다.
- **② Top-down(목표에서 당겨오기):** Raft를 목표로 걸고 필요할 때 기초를 끌어온다. 동기는 강하지만 **구멍(gap)** 위험이 있다.

> **정답은 둘 중 하나가 아니라, "무엇을 앞에 깔고 무엇을 당겨올지"를 나누는 것이다.** 모든 기초가 동등하게 필수인 게 아니다.

학부 CS를 백엔드/시스템 목표 기준으로 냉정하게 우선순위화하면:

| 분야 | 우선순위 | 이유 |
|------|:---:|------|
| **자료구조 & 알고리즘** | 🔴 필수·선행 | 피라미드의 진짜 바닥 + **탑티어 면접의 직접 필터** |
| **운영체제 (OSTEP)** | 🔴 필수 | 동시성·메모리·영속성. 데드락·savepoint 경험의 이론적 뿌리 |
| **컴퓨터 구조 (CSAPP)** | 🟡 있으면 좋음 | 캐시·메모리·CPU. 급하진 않음 |
| **네트워크** | 🟡 필요시 당겨오기 | HTTP/WebSocket 직관 이미 있음 |
| **데이터베이스 내부** | 🟢 나중 (DDIA로) | 이미 실무로 씀 |
| **이산수학·계산이론** | ⚪ 스킵 가능 | 백엔드/시스템엔 거의 안 쓰임. 겁먹지 말 것 |

> 채워야 할 기초의 실체는 **자료구조·알고리즘 + OS 두 개**다. 4년치 학위가 아니라. 나머지는 당겨오거나, 이미 갖고 있거나, 지금은 안 해도 된다.

**자료구조·알고리즘을 맨 앞에 까는 이유**는 일석이조라서다. ① 모든 것의 바닥이고, ② 탑티어 면접의 하드 필터다(구글·메타 면접의 절반). "기초 채우기"인 동시에 "면접 준비"라, 시간이 이중으로 회수된다.

## 7. 최종 사다리 — 지금부터 Raft까지

```
                 ┌─────────────────────────────┐
      [정상]     │   6.824 / DDIA (Raft 구현)   │  ← 분산시스템
                 └──────────────▲──────────────┘
                 ┌──────────────┴──────────────┐
      [3층]      │   네트워크 (필요시 당겨오기)    │
                 └──────────────▲──────────────┘
                 ┌──────────────┴──────────────┐
      [2층]      │   OS(OSTEP) + 구조(CSAPP)     │  ← 내 경험의 이론화
                 └──────────────▲──────────────┘
                 ┌──────────────┴──────────────┐
      [1층]      │  ★ 자료구조 & 알고리즘 ★       │  ← 여기부터 시작
                 └─────────────────────────────┘

  ※ 나는 2·3층에 이미 "경험적 발판"이 있다 (HA failover, 크래시 복구, QPS).
     그래서 1층(DS&A)만 선행하고, 2·3층은 프로젝트와 병행 가능.
```

각 단계를 **내가 이미 한 것**과 연결하면 남 얘기가 아니라 내 얘기가 된다.

| 🪜 | 단계 | 내용 | 기존 경험과의 연결 |
|----|------|------|-------------------|
| 0 | 관점 전환 (지금, 0원) | 블로그를 "웹개발 로그"가 아니라 **"분산시스템 실전 기록"** 으로 재정의 | 지난 글들이 이미 증거 |
| 1 | 자료구조·알고리즘 (2~4개월, 선행) | Big-O 사고, 해시·트리·그래프·정렬 직접 구현 | QPS 스케일링 |
| 2 | OS 형식적 기초 (4~6주) | OSTEP: 동시성(lock·CV) + 영속성(WAL·journaling) | 데드락 / savepoint |
| 3 | 네트워크·RPC 감각 (2~3주, 가볍게) | "네트워크는 끊기고 메시지는 유실·중복·지연된다. 그래도 옳게?" | WebSocket 경험 |

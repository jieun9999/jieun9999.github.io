**2026년 7월 6일부터 9월 9일까지 위블로그를 만들고 베타를 운영한 기록**을 남긴다. 글을 정리하면서 9월 18일에 검색 화면도 다시 확인했다. 그 날짜가 필요한 곳에는 따로 적었다.

8월 18일에 AI 블로그 서비스 베타를 열었다. 그 전에는 “구글이 이 글을 검색 결과에 넣어 줄까?”를 붙잡고 만들었다. 베타를 연 뒤에는 질문이 바뀌었다. “왜 다시 안 쓰지?”, 더 정확히는 “이걸 돈을 내고 쓸 사람은 누구지?”였다.

### 지금 상태 — 실제 사용자 75명, 블로그 86개가 알아서 돌고 있다

회고 자료에 잡힌 실제 사용자는 75명, 개설된 블로그는 201개였다. 그중 86개는 자동 발행을 이어가고 있었고, 발행된 글은 4,691편이었다. 제품은 돌아갔지만, 이 숫자만으로 계속 돈을 낼 사람이 누구인지는 알 수 없었다.

지금 와서 보면 베타 전에는 만드는 데 시간을 썼고, 베타 후에는 왜 안 쓰는지를 알아봤다.

앞에서는 검색 색인, 도메인, 글 구조, 글감, 비용, UX, 배포를 차례로 다룬다. 뒤에서는 채널, 재방문, 로그인, 고객 질문, 운영 자동화, B2C/B2B 갈림길을 거치며 “누가 쓰나?”라는 질문으로 좁혀 간다.

![베타 전후 작업 타임라인. 원본의 ‘앞 9주’ 표기는 실제 날짜 범위와 달라, 본문에서는 8월 18일 전후로 구분했다.](/images/poc-pivot/timeline.png)

> [!NOTE]
> 회고 자료에서 발췌한 화면은 회원 이름만 가렸다. 커버에는 당시 논의 사진을, 검색 노출 사례에는 9월 18일 시크릿 모드에서 직접 확인한 화면을 넣었다.

## 1\. 베타 전 — 검색 결과에 들어갈 수 있나

7월 6일부터 8월 17일까지, 베타 전 판단의 출발점은 “구글이 이 글을 검색 결과에 넣어 줄까?”였다.

처음부터 글을 만들 수 있는지는 고민하지 않았다. LLM은 문장을 만들었다. 문제는 그 글이 그다음 단계까지 무사히 가느냐였다.

```plaintext
글감 찾기
  ↓
출처 수집
  ↓
본문 생성과 구조 검사
  ↓
발행 · 도메인 연결
  ↓
검색 노출과 외부 접근 관찰
```

블로그 글은 생성했다고 끝나지 않는다. 공개 주소에서 열리고, 검색엔진이 읽고, 사람이 봐도 믿을 만한 출처가 있어야 한다. 베타 전에는 멋대로 나가던 글을 멈추고, 검색 결과까지 갈 수 있는 글을 안정적으로 내보내는 데 집중했다.

### 기본 주소와 개인 도메인의 검색 결과가 달랐다

기본 주소로 발행한 글과 개인 도메인으로 발행한 글을 `site:` 명령으로 직접 확인했을 때, 검색 결과에서 발견되는 비율이 크게 달랐다.

| 확인 대상 | 발행 글 | 검색에서 확인한 글 | 비율 |
| --- | ---: | ---: | ---: |
| 기본 주소 `*.witim.blog` | 3,040편 | 224편 | 7.4% |
| 개인 도메인 `coinmanual.blog` | 98편 | 92편 | 93.9% |

![기본 주소와 개인 도메인을 나란히 비교한 실제 검색 화면. 왼쪽은 224/3,040편(7.4%), 오른쪽은 92/98편(93.9%)이며 개인 도메인은 결과가 9페이지까지 이어졌다.](/images/poc-pivot/indexing-comparison.jpg)

당시 `site:` 검색으로 확인한 숫자다. 검색 결과 수를 전체 색인 수라고 부를 수는 없고, 주제나 발행 시점, 외부 링크 조건을 맞춘 실험도 아니었다. 그래도 주소 하나가 이렇게 다르게 보인다는 사실만으로, 도메인을 발행 뒤의 부가 설정으로 둘 수는 없었다.

### 그래서 도메인을 제품 안에서 사고 붙이게 만들었다

![주소와 색인 관찰에서 도메인 구매·연결 기능으로 이어진 판단. 검색 → 결제 → 등록 → 연결을 하나의 흐름으로 만들었다.](/images/poc-pivot/domain-purchase-flow.png)

당시 살펴본 워드프레스와 인블로그도 처음부터 도메인 구매·연동을 강조하고 있었다. 제품 판단도 바뀌었다. 사용자가 외부에서 도메인을 사고, DNS를 설정하고, 연결 상태를 확인해야만 실험을 시작할 수 있다면 글 생성 기능이 좋아도 중간에서 막힌다. 그래서 도메인 검색, 결제, 등록, 연결 확인을 제품 안으로 넣었다. `workb.xyz`에서 `witim.blog`를 거쳐 커스텀 도메인 연결을 기본 흐름으로 잡았고, 회고 당시에는 블로그 201개 중 36개가 자기 도메인을 쓰고 있었다.

도메인 연결에서는 “요청을 보냈다”와 “서비스가 열린다”를 구분했다. 실패하면 자동으로 전액 환불했고, 실제 서비스가 열렸을 때만 연결된 상태로 바꿨다. 대표 주소를 정하지 않아 사이트 전체가 색인에서 빠진 적도 있었다. 도메인은 발행 뒤에 붙이는 설정이 아니라 검색 PoC를 시작하기 위한 조건이었다.

## 2\. 글 구조 — 출처 없으면 쓰지 않는다

그다음에는 글의 모양을 정했다. 검색 상단 글을 뜯어보니 질문형 제목, 본문 위의 즉문즉답 요약, 항목마다 3~5줄로 나눈 목차와 본문, FAQ와 참고 자료가 반복됐다. 이걸 “권장 가이드”로만 두면 글마다 결과가 달라진다. 그래서 생성기가 반드시 지키는 규칙으로 넣었다.

![실제 생성 글의 상단 요약과 하단의 참고 자료·FAQ. 작성자 이름만 가렸다.](/images/poc-pivot/article-structure.png)

가장 엄격하게 둔 규칙은 출처였다. 출처를 찾지 못하면 글을 만들지 않았다. 문장이 자연스럽다는 이유만으로 발행하면 보기 좋은 글만 쌓이고, 나중에 확인할 근거는 남지 않는다.

출처 규칙은 특히 건강, 금융처럼 잘못된 정보의 비용이 큰 주제에서 중요했다. 생성 전에 참고할 문서를 찾고, 근거가 준비되지 않으면 다음 단계로 넘기지 않았다. 예시 글에도 공공기관의 자료를 출처로 넣었다.

### AI가 실제로 발행한 글을 가져간다

그 구조로 만든 글이 구글 AI 개요에 출처로 인용되는 장면을 실제 답변 화면에서 봤다. 나중에 병원·부동산으로 PoC를 좁힐 때 이 경험이 기술적인 출발점이 됐다.

![구글 AI 개요가 위블로그 글을 출처로 인용한 화면. ‘혼인서약서 샘플 작성 순서’를 검색했을 때 생성한 글이 오른쪽 출처 카드에 노출됐다. AEO 성공 사례.](/images/poc-pivot/aeo-citation-success.png)

![AI가 가져간 글을 글 단위로 보여주는 제품 화면. 발행 75편 중 로봇이 읽은 글 74편, AI 답변 후보 26편, 인용으로 집계한 글 24편이 표시되어 있다. 회원 이름만 가렸다.](/images/poc-pivot/ai-crawl-dashboard.png)

서버 접속 기록으로 어느 AI 크롤러가 어떤 글에 접근했는지를 글 단위로 관찰했다. 검색 순위표만으로 보이지 않는 외부 접근을 사용자가 제품 안에서 확인하게 만든 화면이다.

앞의 크롤링 대시보드에서 보여준 읽힘·인용 수치는 제품의 집계 기준에 따른 관찰값이다. 답변 화면에서 직접 확인한 사례와는 구분해서 봤다. 크롤러의 방문만으로 실제 답변의 인용을 증명할 수는 없다.

### 검색 결과 상단에 실제로 노출됐다

AI 인용과 별개로, 일반 검색에서 발행한 글이 어디에 노출되는지도 확인했다. 9월 18일 구글에 로그인하지 않은 시크릿 모드에서 두 검색어를 다시 검색했다. `site:`로 특정 도메인을 지정하지 않아도 발행한 블로그 글이 일반 검색 결과에 나타났다.

![시크릿 모드에서 ‘용산 재개발 토지거래허가구역’을 검색한 결과. 파란색으로 표시한 영역에 발행한 블로그 글이 노출됐다. 2026년 9월 18일 확인.](/images/poc-pivot/search-incognito-yongsan.png)

![시크릿 모드에서 ‘마포구분양 신축 아파트’를 검색한 결과. 이 검색어에서도 발행한 블로그 글이 일반 검색 결과에 나타났다. 2026년 9월 18일 확인.](/images/poc-pivot/search-incognito-mapo.png)

두 화면에서 확인한 것은 **일반 검색 결과에 글이 노출됐다는 사실**까지다. 생성한 문서가 계속 검색에 노출되고 실제 유입으로 이어지는지는 아직 남은 문제였다.

## 3\. 글감 — 제일 어려운 건 무슨 글을 쓸까였다

글 구조를 잡고 나니 앞단이 더 크게 보였다. 사용자는 “좋은 글을 써줘”보다 먼저 “무슨 글을 쓰면 되지?”에서 막힌다.

큰 키워드는 경쟁이 세고, 수요가 없는 키워드는 써도 찾아올 사람이 없다. 초보 사용자가 그 사이에서 쓸 만한 주제를 고르기는 쉽지 않았다.

여러 시도 끝에 구글과 네이버 자동완성을 글감 후보의 출발점으로 삼았다. 예를 들어 ‘특수건강검진’ 하나를 넣으면 후보 7개가 바로 나왔다. 각 후보 옆에는 어느 검색엔진에서 가져왔는지 표시했다.

![키워드 하나에서 나온 자동완성 후보. 오른쪽 G·N 배지로 구글·네이버 출처를 구분한다.](/images/poc-pivot/keyword-discovery.jpg)

자동완성은 검색어 형태의 후보를 빠르게 준다. 무엇보다 사람들이 실제로 검색창에 입력한 표현을 찾는 단서라고 봤다. 두 엔진을 동시에 불러 합쳤고, 이 단계에서는 별도 유료 검색 API 비용 없이 후보를 모을 수 있었다. 한 번 찾은 후보는 7일간 저장했다.

자동완성이 성과를 보장하는 것은 아니다. 자동완성에 나온다고 새 블로그가 상단에 오르거나 유입이 생기는 것도 아니다. 이 단계에서 필요했던 건 수익이 보장된 키워드가 아니라, 사용자가 빠르게 살펴볼 후보였다.

## 4\. 속도와 비용 — 줄이기 전에 먼저 쟀다

검색에 잡히는 글이 나와도 바로 사용자 검증으로 넘어갈 수는 없었다. PoC를 반복하려면 생성 비용과 대기 시간을 감당할 수 있어야 했다.

가장 오래 걸리고 비싼 단계는 출처를 모으는 쪽이었다. 출처 검색에 쓰는 DataForSEO는 부를 때마다 돈이 나갔다. 그래서 먼저 로그를 나눴다. 어느 단계가 몇 번 호출됐는지, 무엇 때문에 실패했는지, 캐시로 넘어갔는지, 실제 과금이 있었는지부터 남겼다.

![잰다 → 나눈다 → 저장한다 → 감시한다. 과금 로그에서 시작해 형제 글감의 검색 결과 공유, 7일 캐시, 잔액 알림으로 이어진 비용 개선 순서.](/images/poc-pivot/cost-measurement.png)

그다음에야 줄일 단위가 보였다.

- 같은 주제의 형제 글감은 검색 결과를 공유한다.
- 한 번 찾은 문서는 7일간 캐시해 재사용한다.
- 계속 실패하는 사이트는 비싼 재시도를 반복하지 않는다.
- 외부 API 사용 상태는 문제가 되기 전에 알림으로 확인한다.

이 순서가 방법이었다. “빨라졌다”라고 말하는 것보다 “무엇을 재고, 어떤 호출을 생략했고, 얼마만큼 줄었는지”를 말할 수 있어야 했다.

### UX — 화면 오른쪽 흐름을 따라가면 발행까지

개인 콘솔에는 지금 어느 단계인지, 남은 작업이 무엇인지, 다음 발행이 언제인지를 한 흐름으로 보여줬다. 단계가 넘어갈 때는 움직임을 넣었다. 하지만 화면이 매끄러워 보이려면 기다리는 시간부터 짧아야 했다.

![키워드 선택부터 발행까지 이어지는 개인 콘솔. 오른쪽에 현재 단계와 다음 발행 시각이 보인다.](/images/poc-pivot/publishing-flow.jpg)

| 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 온보딩 첫 대기 | 21.9초 | 8.6초 |
| 도메인 검색 | 8.2초 | 1.4초 |
| 첫 화면 데이터 | 596KB | 189KB |
| 미리보기 서버 호출 | 17번 | 1번 |

회고 당시 정리한 개선 전후 수치다. 키워드를 모두 받은 뒤 다음 화면으로 넘기는 대신, 먼저 시작하고 뒤에서 받도록 바꿨다. 전체 계산량을 전부 없앤 것은 아니었다. 사용자가 처음 기다리는 순서도 함께 바꿨다.

## 5\. 배포 — 무서우면 아무것도 못 고친다

초기에는 배포할 때마다 사이트가 10초 넘게 죽었다. 고객 도메인이 내가 담당하던 서비스의 서버를 가리키고 있으면, 배포 중단은 곧 고객 블로그의 중단이었다.

그래서 관리자 화면과 API에 blue-green 배포를 적용했다. 새 버전을 옆에 띄우고 정상 상태를 확인한 뒤 전환했다. 이전 버전은 바로 지우지 않고 멈춰 둬서, 문제가 생기면 20~30초 안에 되돌아갈 수 있게 했다.

다만 이건 고객 수요를 증명한 이야기는 아니다. 피봇을 하려면 실험을 자주 바꿔야 하고, 그러려면 되돌리는 비용이 낮아야 한다. 배포가 무서우면 고쳐야 할 문제를 알아도 손을 대지 못한다. 되돌리는 비용을 낮추고 나서야 디자이너도 직접 화면을 고칠 수 있었다.

## 6\. 만들었다가 접은 것들

베타 전후로 만든 것 중에는 오래 살아남지 못한 것도 많았다. 회고 자료에는 여섯 가지를 타임라인으로 그렸다. 홍보 문단, 글감 자동 생성, 질문 기반 글감, 두 번째 글쓰기 엔진, 초대코드 가입, 위팀 로그인. 어떤 것은 한 달 가까이 갔고, 어떤 것은 며칠 만에 접었다.

![만들었다가 접은 여섯 가지. 막대 길이는 각 접근을 유지한 기간이다.](/images/poc-pivot/discarded-experiments.png)

| 홍보 문단 | 29일 |
| 글감 자동 생성 | 23일 |
| 지식iN 글감 | 5일 |

### 지식iN 글감을 닷새 만에 접은 이유

![지식iN 글감 실험을 접은 두 이유와 나중에 확인한 데이터. 분야별 질문 밀도가 달랐고, 질문을 검색어로 정규화하는 시간도 길었다.](/images/poc-pivot/keyword-experiment.png)

사람들이 실제로 물어본 질문에서 뽑으면 가장 진짜 수요에 가까울 것이라고 봤다. 설계 문서를 네 장 쓰고 구현했지만, 기본 재료로 쓰기에는 두 가지 문제가 있었다.

**분야가 치우쳐 있었다.** 일상·연예에는 질문이 많았지만, 재테크·시사·정치 쪽은 질문이 적었다. 여러 분야에서 일관되게 후보를 뽑아야 하는 서비스의 기본 입력으로는 밀도가 고르지 않았다.

**정규화가 느렸다.** 질문 제목과 본문 스니펫을 검색어로 다듬는 데 시간이 걸렸다. 버튼을 누르면 바로 후보가 나오길 기대하는 흐름과 맞지 않았다. 질문을 더 많이 모으는 것만으로 두 문제를 해결할 수는 없었다.

베타 이후인 9월 7일, 158개 사이트와 4,389편을 대상으로 집계해 보니 재테크·금융이 글당 조회 **0.900**, 대시보드의 AI 인용 지표 **3.84**로 두 지표 모두 가장 높았다. 회고 자료에 남은 숫자이고, 앞의 단일 블로그 집계와는 대상과 시점이 다르다. 문화·취미와 IT는 해당 지표가 0이었다. 나중에 이 숫자를 보고 나서야, 성과가 나온 분야가 지식iN 질문이 적었던 분야와 겹친다는 걸 알았다. 처음부터 알고 접은 것은 아니다. 그때는 커버리지와 속도가 맞지 않아 접었고, 고객 반응은 그 뒤에 확인했다.

## 7\. 베타 후 — 가입 수가 아니라 채널 리스크를 봤다

8월 18일부터 9월 9일까지는 왜 안 쓰는지 알아봤다. 사람이 실제로 들어와야만 보이는 것들이 있었다.

베타를 열자 사용자가 들어왔다. 첫 스레드 게시물이 반응을 얻으면서 하루에 50명이 들어왔고, 초반에는 DM 자동화와 초대코드로 가입을 연결했다.

첫 반응은 좋았다. 며칠 뒤에는 외부 링크 유입을 위해 돌리던 DM 자동화 때문인지 스레드 계정이 삭제됐다. 유입을 만들던 방법이 채널 자체를 잃게 만들 수 있다는 걸 그때 알았다.

![첫 스레드 게시물에 달린 반응. 좋아요 112개와 댓글 558개가 달렸다. 2026년 8월 26일 확인.](/images/poc-pivot/threads-account-deletion.png)

| 가입 구간 | 실제 사용자 |
| --- | ---: |
| 8월 18일–31일 · 초대코드 가입 | 68명 |
| 9월 1일–9일 · 누구나 가입 | 7명 |

![첫 스레드 반응과 가입 방식별 유입을 정리한 회고 화면. 가입 정책의 변화와 채널 운영의 변화가 같은 시기에 일어났다.](/images/poc-pivot/channel-risk.png)

실제 사용자 수의 증감보다 더 크게 남은 건 채널 리스크였다. 계정이 폭파된 원인을 추적하면서 외부 링크 유입을 위한 DM 자동화를 원인 후보로 봤고, 이후 스레드 DM 사용을 지양하기로 했다. 스레드는 DM 홍보 수단이 아니라 콘텐츠 채널로 써야 했다. 링크마다 출처를 붙여 유입을 확인하고, 어떤 게시물이 어떤 행동으로 이어졌는지를 보기 시작했다.

## 8\. 재방문 — 다시 오게 할 트리거를 만들었다

자동 발행이 되더라도 사용자가 다시 들어올 계기는 필요했다. 그래서 발행 현황과 무료 기간 종료를 알려 재방문을 유도하는 알림톡과 이메일 템플릿을 만들었다.

이메일은 발송 대기열과 이력부터 만들고, 발행 현황과 무료 기간 종료 등 템플릿 21종을 준비했다. 도착·반송·열람·클릭도 따로 봤다. 사용자가 받아서 확인하는 횟수는 이메일보다 카카오 알림톡이 더 많았다.

![발행 현황을 알려주는 이메일과 카카오 알림톡. 회원 이름만 가렸다.](/images/poc-pivot/notifications.png)

알림을 만들었다고 재방문이 좋아졌다고 말할 수는 없다. 대신 “사용자가 다시 올 이유를 어떻게 알릴까”라는 문제를 따로 볼 수 있게 됐다. 자동화가 잘될수록 결과를 알려주는 장치가 필요했다. 웹푸시와 커뮤니티도 함께 검토했다. 우리가 부르는 계기와 사용자가 스스로 찾아오는 이유는 달랐다.

## 9\. 로그인과 온보딩 — 나중에 고치면 늦는다

처음에는 위팀 허브 로그인을 붙였다. 위팀 허브는 회사 자체 회원가입·로그인 시스템이다. 회사 계정으로 쓰는 흐름을 먼저 붙이다 보니 개인 사용자에게는 가입 장벽이 됐다. 이메일·나이·실명·전화번호 중 무엇을 어떤 동의로 받고 어디에 쓸지, 가입 이후 어떤 분석과 안내를 할지까지도 충분히 정리하지 못했다. 문을 열고 나서야 사용자의 연령대와 유입 경로를 함께 봐야 한다는 필요가 드러났다.

개인 사용자에게 익숙한 원클릭 카카오 로그인으로 흐름을 정리했다. 동의받아 전달된 이름·연락처·연령대를 저장하고, 이미 받은 전화번호는 화면에서 다시 묻지 않았다. 구현 중에는 선택 항목이라고 생각한 값이 요청 설정 때문에 동의 화면에서 필수처럼 나타나는 문제도 만났다. 요청 항목과 동의 화면을 다시 맞췄고, 처리방침도 실제 항목에 맞춰 세 차례 고쳤다.

로그인 버튼 하나로 온보딩이 끝나지는 않았다. 가입을 편하게 만드는 일과, 이후 분석과 안내에 필요한 정보·동의를 정하는 일을 같이 설계해야 했다.

## 10\. B2C 비즈니스의 한계 — 부업·주부 고객은 19만 원을 낼 수 없었다

B2C로 문을 열고 나니 고객이 실제로 어떤 생각을 하는지 들을 수 있었다. 오픈채팅방에는 이런 말이 올라왔다.

> “그것도 수익화가 되나요?”
>
> “어떻게 넣어요? 도메인을 사야 해요?”
>
> “사용 수수료 정도는 뽑을 수 있을지 모르겠네요”

![오픈채팅방에 올라온 실제 사용자 질문. 회원 이름과 닉네임만 가렸다.](/images/poc-pivot/customer-questions.png)

네이버 블로그에 익숙한 주부·부업 사용자에게는 구글 검색을 거쳐 독립된 블로그로 들어온다는 방식 자체가 낯설었다. 기능을 더 넣기 전에 이 간극부터 이해해야 했다.

내가 해결했다고 생각한 문제는 글쓰기의 번거로움이었다. 사용자가 묻는 것은 그보다 앞에 있었다. “왜 이 방식으로 블로그를 운영해야 하는가”, “만든 글이 내 목적에 어떻게 연결되는가”였다.

당시 비교하던 인블로그 같은 제품은 기업과 글로벌 시장을 향한 SaaS였다. 같은 콘텐츠 도구라도 고객이 비용을 회수하는 방식은 달랐다. 기능을 따라가기 전에, 내가 맡은 제품의 고객이 어떤 결과를 사는지부터 정해야 했다. 그래서 고객을 고르는 기준도 **19만 원을 회수할 수 있는 사람인가**로 바뀌었다.

그래서 가격이 비싸다는 말도 다르게 들렸다. 단순히 숫자가 높다는 뜻이 아니라, 본전이 보이지 않는다는 뜻에 가까웠다. 새 블로그를 만들고, 별도 도메인을 붙이고, 검색과 AI 답변에서 발견되기를 기다리는 과정이 자신의 수익 구조와 연결되지 않으면 사용자는 계속 쓸 이유를 찾기 어렵다.

## 11\. 운영 — 리소스·비용 임계치를 넘으면 개발자에게 이메일이 가도록

베타 전에는 기능을 만드는 데 바빴고, 베타 후에는 운영을 버틸 장치가 필요했다. 서버 자원, 외부 API 상태, AI 계정별 사용량을 한 화면에서 보고, 리소스나 비용이 임계치를 넘으면 개발자에게 이메일이 가도록 했다. 그라파나 화면은 30초마다 갱신했다.

![그라파나 대시보드 전체 화면. CPU·메모리·디스크, 외부 API 잔액, 계정별 사용량과 서버 부하를 한 화면에서 확인했다.](/images/poc-pivot/monitoring.jpg)

주간 필요량이 계정 하나의 한도 대비 112%여서 두 계정을 운영했다. 주 계정 사용량이 80%에 도달하면 보조 계정으로 넘어가고, 한도가 초기화되면 다시 돌아오게 했다. 이 자동 전환이 제품의 가치를 증명하는 건 아니다. 그래도 사용자가 없는 시간에 사람이 하던 일을 서버가 처리해야 베타를 계속 돌릴 수 있었다.

회고 화면의 EvoLink 잔액은 **$63.67**, 당시 소모 속도로 계산한 잔여 기간은 **20.8일**이었다. 잔액만 보여주는 것보다 언제 손을 써야 하는지를 같이 보여줘야 했다.

![EvoLink 잔액이 최근 7일 평균 소모 속도 기준 5일치 아래로 내려갔을 때 받은 그라파나 알림. 조치할 항목과 대시보드 링크를 함께 보냈다. 수신자 이름만 가렸다.](/images/poc-pivot/monitoring-alert.png)

알림도 만든 뒤 줄였다. 규칙은 24개에서 21개로 줄이고, 잔액 알림은 4시간 간격으로 두 번까지만 보내게 했다. 실제 운영에서는 너무 많은 알림이 판단을 흐린다. 보고 싶은 것은 모든 사건이 아니라 행동해야 하는 사건이었다.

## 12\. 방향 결정 — B2C와 B2B를 놓고 갈랐다

9월이 되자 방향을 두 갈래로 나눴다.

![2026년 9월, B2C와 B2B를 화이트보드에 나눠 적으며 방향을 정하던 자리. 커버와 같은 원본 사진이다.](/images/poc-pivot/pivot-whiteboard.jpg)

| 방향 | 대상 | 제공하려는 가치 |
| --- | --- | --- |
| B2C | 기존 네이버 블로그 운영자 | 익숙한 블로그로 글을 내보내기 |
| B2B | 이미 자체 사이트가 있는 업체 | SEO·GEO 최적화로 검색과 AI 답변에서 발견될 문서 만들기 |

B2C에서는 새 블로그를 처음부터 운영하게 하기보다 네이버 블로그 내보내기를 검토했다. 이 방향에서는 글감 자동화를 빼기로 했다. 만들 수 있는 기능을 모두 넣는 것보다, 기존 운영자의 작업에 어디까지 들어갈지를 다시 정한 것이다.

B2B에서는 사이트가 있는데도 검색이나 AI 답변에서 충분히 발견되지 않는 문제를 봤다. 글을 대신 쓰는 것에서, 사업자의 유입에 필요한 문서를 만드는 쪽으로 질문이 옮겨갔다.

방향을 정하고도 남은 질문은 그대로였다. **“항상 몇 명이 유입되는지”를 보여줄 수 있는가.**

그래도 앞에서 만든 것은 다시 쓸 수 있었다. 출처 기반 글 구조, 검색에 잡히는 발행, 도메인 연결, 크롤러 관찰, 배포 안정성은 남았다. 달라진 건 “누구에게 왜 필요한가”라는 질문이었다.

```plaintext
베타 전 검증한 것
글감 → 생성 → 발행 → 검색·인용 가능성

피봇 후 검증하려는 것
고객의 목적 → 필요한 문서 → 발견 여부 → 유입 → 고객이 느끼는 가치
```

### 본전이 눈에 보이는 고객 — 병원과 부동산

![병원·부동산 대상의 브랜드 블로그, 작업 흐름, 자영업용·엔터프라이즈 요금제를 정리한 화이트보드.](/images/poc-pivot/target-pricing-whiteboard.jpg)

고객을 좁히는 기준도 달라졌다. **한 건의 문의나 계약이 갖는 가치를 설명할 수 있는 고객**을 보기 시작했고, 병원과 부동산으로 타깃을 좁혔다. 당시 정리한 자영업용 요금은 19만 원, 엔터프라이즈는 별도 협의였다. 중개보조원이나 병의원 사무직원처럼 실무에서 콘텐츠를 관리하는 사람을 떠올렸고, 화성중앙종합병원 브랜드 블로그도 구체적인 대상으로 놓았다. 한 건의 계약 가치와 이용료를 비교할 수 있다면, 콘텐츠가 왜 필요한지와 본전을 어떻게 회수할지를 같은 문장 안에서 설명할 수 있다고 봤다.

접었던 기능이 다시 의미를 갖기도 했다. 개인은 카카오로, 회사 고객은 위팀 계정으로 팀 단위로 쓰는 흐름을 잡으면서 위팀 로그인이 다시 필요해졌다. 피봇은 앞서 만든 것을 모두 버리는 일이 아니라, 누구의 작업에 필요한지를 다시 따져보는 일이었다.

## 13\. 그래서 지금 풀어야 할 문제

베타 전에는 기술적으로 만들 수 있는지를 확인했다. 검색에 잡히는 글을 만들고, 출처를 붙이고, AI 답변에 인용되는 사례를 봤다. 반복 발행을 버틸 운영 기반도 만들었다.

베타 후에는 팔 수 있는 곳을 찾아야 했다. 사용자는 “글이 자동으로 나간다”는 이유만으로 움직이지 않았다. 자신에게 어떤 결과가 돌아오는지 알아야 했다. 어디서 들어왔는지, 왜 다시 와야 하는지, 가입 때 무엇을 받는지, 만들어진 문서가 사업 결과로 이어지는지를 각각 확인해야 했다.

병원이나 부동산을 고를 때 AI에게 묻는 상황을 생각하면, 작은 업체에는 불리한 출발점이 있었다. 큰 곳은 기사와 후기와 문서가 쌓이지만, 작은 곳은 홈페이지 하나가 전부인 경우가 많다. 외부에서 참고할 문서가 부족하면 AI가 업체를 설명할 근거도 부족하다.

### 병원·부동산 전문 블로그와 대행사 제휴로 BM을 다시 설계했다

그 빈자리를 채우는 방향으로 BM을 다시 설계했다. 병원·부동산을 위한 전문 블로그를 만들고, 이를 대신 운영하려는 대행사와 제휴하는 방식이다. 네이버 블로그 알고리즘만 바라보기 어려워진 상황에서, 구글에 색인되고 검색 상단에 노출되는 채널을 갖고 싶어 하는 고객이 분명히 있었다. 회고 시점에는 이미 기존 고객을 확보해 두었고, 앞서 만든 출처 기반 글 구조와 발행 흐름을 병원·부동산 전문 블로그에 적용하고 있었다.

대행사와 제휴하면 고객은 직접 글을 만들고 운영하는 부담을 덜 수 있고, 대행사는 고객에게 검색 노출이라는 결과를 제안할 수 있다. 위블로그는 그 안에서 전문 블로그를 만들고, 출처가 있는 문서를 꾸준히 발행하는 제품이 된다. 남은 과제는 이 구조로 유입과 문의가 얼마나 생기는지 계속 증명하는 일이다.

### 만들 수 있다는 걸 확인하고, 팔리는 구조로 다시 설계했다

기술적으로 만들 수 있다는 건 확인했다. 이제는 병원·부동산 전문 블로그와 대행사 제휴라는 BM으로 이미 확보한 고객을 확장하고, 네이버 블로그의 불확실성이 커진 시점에 구글 색인과 상단 노출을 원하는 고객에게 어떤 결과를 줄 수 있는지 검증하려 한다.

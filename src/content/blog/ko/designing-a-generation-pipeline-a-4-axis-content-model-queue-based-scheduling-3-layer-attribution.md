## 들어가며

<a id="tldr"></a>

이 글은 Threads 마케팅 에이전트(Hermes)를 만든 기록의 2편입니다. Hermes는 사람이 Discord에 참고할 커뮤니티 게시물의 URL을 올리면 동작합니다. 봇이 그 게시물을 바탕으로 Threads용 본문과 댓글 3개, 이미지를 만들고, 정한 시각에 발행한 뒤 반응과 클릭을 수집합니다. 다루는 소재는 자동차입니다.

[1편](/ko/blog/designing-a-crawler-that-beats-three-tiers-of-anti-bot-from-tls-fingerprints-to-cdp-detection/)에서는 여러 사이트의 게시물을 수집해 `{title, body, comments[], images[]}`라는 하나의 형태로 정리했습니다. 이번 글은 그다음 단계입니다. 정리된 게시물로 Threads 글을 만들고, 예약 발행하고, 성과를 측정하는 과정을 다룹니다.

이 과정에서 세 가지 문제를 해결해야 했습니다.

1.  **AI가 만든 게시물이 소재와 상관없이 비슷한 기사체로 돌아갔습니다.** 게시물을 구성하는 기준을 후크·화자·본문 형식·주제의 네 가지로 나누고, 각각 따로 고를 수 있게 바꿨습니다. 이 구조는 처음부터 설계한 것이 아니라 다섯 번의 수정을 거쳐 나왔습니다.

2.  **예약 발행에서 같은 글이 두 번 올라가면 안 됐습니다.** 발행 SaaS를 쓰지 않고 SQLite 큐와 1분 주기 워커로 직접 만들었습니다. 워커가 발행 전에 대상 행을 먼저 잠그게 해서 같은 글이 한 번만 발행되도록 했습니다.

3.  **Threads는 클릭과 전환을 알려 주지 않고, 직접 기록한 클릭의 약 90%는 봇이었습니다.** 자체 리다이렉터로 클릭을 기록하고 전환까지 연결했습니다. 대시보드는 봇 클릭을 기본으로 제외하고, 데이터가 비어 있어도 잘못 읽히지 않게 만들었습니다.

> 범위: 지금은 측정 인프라를 먼저 갖추는 단계입니다. 이 글은 시스템 설계와 문제 해결의 기록입니다. 참여율(ER)·전환율(CVR)·광고 수익률(ROAS) 같은 비즈니스 성과는 표본이 쌓여야 판단할 수 있으므로 여기서는 주장하지 않습니다.

## AI가 만든 게시물은 왜 자꾸 비슷해졌을까?

생성 결과가 비슷해지는 문제는 한 번에 해결되지 않았습니다. 구조를 다섯 번 바꿨고, 매번 같은 실패가 왜 반복되는지 추적하다가 다음 원인을 찾았습니다. 아래는 그 순서입니다.

### 정리된 정보만 내놓던 '큐레이터'를 '커뮤니티 오퍼레이터'로 바꿨습니다

초기 봇의 정체성은 "최신 트렌드 자동차 큐레이터"였습니다. 톤 규칙을 계속 추가해도 결과물은 깔끔한 뉴스 리포트처럼 나왔습니다. 원인은 톤 규칙보다 상위에 있는 정체성 설정이라고 판단했습니다.

> 큐레이터는 정보를 정리하고, 오퍼레이터는 반응을 설계합니다. 플랫폼 알고리즘과 커뮤니티는 _정리된 정보_보다 _감정과 참여_에 반응합니다. 정체성이 "큐레이터"라면 결과물은 구조적으로 "읽고 끝"인 글로 수렴합니다. 톤은 정체성을 따라가므로, 정체성을 바꾸지 않으면 톤 규칙이 힘을 갖지 못합니다.

"최신성"에 의존하는 방식에도 구조적인 한계가 있었습니다. 소재가 빠르게 고갈되고, 다른 계정과 차별화되지 않으며, 결국 보도자료를 옮기는 일에 묶입니다. 반면 실제로 반응이 좋았던 콘텐츠는 시기를 타지 않는 후크였습니다. 첫차 후회, 호구 옵션, "그 돈이면…" 같은 주제입니다.

그래서 정체성을 **"반응을 설계하는 커뮤니티 오퍼레이터"**로 다시 정했습니다. 정보를 버린 것은 아닙니다. 정보는 신뢰를 받치는 기반으로 남겼습니다. 정보가 너무 많으면 지루하고, 도발이 너무 많으면 역풍이 붑니다. 목표는 그 중간입니다.

이때 지침 문서의 역할도 나눴습니다. 봇에는 정체성과 지켜야 할 제약을 적은 SOUL 문서와, 실행 절차를 적은 SKILL 문서가 있습니다. 당시에는 이미지 정책, 출력 포맷, 댓글 구성, 본문 길이가 두 문서에 중복돼 실제로 충돌했습니다(댓글 구성은 고정 vs 동적, 길이는 6–9줄 vs 5–7문장). 그래서 숫자·포맷·절차는 SKILL 한 곳에만 두고, SOUL에는 이유와 상한선만 남겼습니다. 같은 규칙의 출처를 하나로 유지하기 위해서입니다.

### 한 분류에 기준 네 개가 섞여 있어 게시물이 여러 유형에 걸쳤습니다

초기에는 게시물 유형을 `content_mode` 하나로 골랐습니다. 값은 네 가지였는데, 표로 정리하면 각각 다른 기준으로 나뉘어 있었습니다.

| mode | 실제 분류 기준 |
| --- | --- |
| `debate_thread` | 의도(논쟁 유발) |
| `buyer_dilemma` | 주제(구매) |
| `rank_bait` | 포맷(리스트) |
| `trend_brief` | 최신성(latest) |

기준이 섞여 있으니 한 게시물이 여러 모드에 동시에 해당하는 경우가 생겼습니다. 특히 `debate_thread`와 `buyer_dilemma`가 자주 겹쳤습니다.

더 큰 문제는 "누가 말하는가"를 정하는 기준이 아예 없었다는 점입니다. 같은 자동차 이야기를 화자만 바꿔 다시 생성할 방법이 없었습니다. 서로 다른 관심사를 enum 하나에 몰아넣은 구조였습니다.

### 기준을 독립된 세 축으로 나눠 조합하게 했습니다

섞여 있던 기준을 세 개의 축으로 나눴습니다.

-   **hook\_engine** — 첫 줄에서 독자를 멈추게 하는 방식: hot\_take, money\_truth, regret\_story, versus, rank\_bait …

-   **persona** — 말하는 사람과 대상 독자: first\_car, young\_budget / purist, tuner, data\_geek …

-   **topic\_tag** — 주제 영역: EV, depreciation, options, tuning …

각 축의 값은 다른 축과 상관없이 고를 수 있습니다. 같은 `regret_story` 후크를 `first_car` 화자로도, `tuner` 화자로도 쓸 수 있습니다. 이렇게 서로 영향을 주지 않는 축을 **직교 축**이라고 부릅니다. 축이 독립적이면 만들 수 있는 조합의 수는 각 축 값 개수의 곱이 됩니다. 그래서 축 하나에 값을 추가하는 것만으로 다양성이 크게 늘어납니다.

축을 나누면서 함께 바꾼 내용은 다음과 같습니다.

-   `debate_thread`는 `hot_take`로 강화하고, `money_truth`·`regret_story`·`versus`를 새로 추가했습니다.
-   persona를 생성할 때 반드시 정하는 입력으로 올렸습니다. 구매자 유형 6종과 매니아 유형 6종입니다.
-   댓글은 고정된 3인 페르소나 세트 대신 본문에 따라 화자를 고르게 바꿨습니다. 본문과 반대 입장인 화자가 반론을 다는 방식입니다.

> **축을 바꾸자 발행 기록이 끊겼습니다.** 발행한 게시물은 발행 원장(publish ledger)에 기록합니다. 이 기록은 같은 조합의 반복을 피하고 성과가 좋은 조합에 가중치를 주는 학습 루프의 입력입니다. 그런데 기록 스크립트의 `validate()`가 예전 모드 4개만 허용하고 있었습니다. 새 축으로 생성한 게시물을 기록하려 하면 `SystemExit`으로 중단됐습니다. 게시물 생성은 됐지만 학습 루프로 가는 입력이 끊긴 것입니다.
>
> 기록 어휘를 v2로 완전히 교체하고, 과거 원장도 같은 어휘로 정규화했습니다. 이 마이그레이션은 여러 번 실행해도 결과가 달라지지 않게 작성했습니다. 콘텐츠 모델을 바꾸면 그 값을 저장하는 데이터 계층도 함께 옮겨야 한다는 점을 확인한 사례입니다.

### 소재 자동 발굴은 만들었지만 운영에서 뺐습니다

세 축 위에 Auto-Pick을 추가했습니다. 간단히 입력하면 봇이 축을 자동으로 고르고 소재까지 찾아 주는 기능입니다. 기능은 동작했지만 운영에서는 제외했습니다.

소재까지 자동으로 발굴하면 주제가 넓게 흩어집니다. 마케팅 채널에는 이미 반응이 검증된 게시물을 골라 올려야 하고, 그 판단은 봇의 휴리스틱보다 사람이 더 잘한다고 봤습니다. 그래서 범위를 **"사람이 소스 URL을 고른다"**로 고정하고 자동 발굴을 제거했습니다. 1편의 원칙 2와 같은 결정입니다. 봇은 고른 소재를 변환하고 다양하게 만드는 일만 맡습니다. 자동화의 범위를 운영 규모에 맞춘 것입니다.

### 세 축으로도 기사체가 나와 본문 형식(format)을 네 번째 축으로 추가했습니다

세 축을 갖췄는데도 본문은 계속 기사체로 돌아갔습니다. 원인을 따라가 보니 hook\_engine은 "왜 멈추고 읽는가", 즉 첫 줄만 결정하고 있었습니다. 본문의 골격을 정하는 축은 없었습니다. 그래서 hook\_engine이 본문까지 떠안았고, 결과적으로 정보를 나열하는 글이 됐습니다.

해결책은 본문 골격을 강제하는 **네 번째 축 `format`**이었습니다.

| format | 골격 | 숫자 상한 |
| --- | --- | --- |
| `list_drip` | TOP/랭킹 리스트, 항목당 한 줄 촌평 | 최소 |
| `owner_stereotype` | "○○ 오너 유형" 공감형 촌평 | 0 |
| `one_line_thread` | 단타 단톡방 미끼, 끊어치는 문장 | 0–1 |
| `fill_in_blank` | "\_\_\_ 사면 \_\_\_ 된다" 식 투표 유도 | 0 |
| `confession` | 1인칭 후회/자랑 스토리 | 0–1 |
| `data_brief` | 정보 요약 형식 — **명시적 요청 시에만** | 높음 |

핵심은 정보 요약 형식인 `data_brief`를 기본값에서 뺀 것입니다. 명시적으로 요청할 때만 쓰고, 기본값은 나머지 5개 커뮤니티 형식 중 하나입니다. 같은 소재도 형식을 바꾸면 다른 게시물이 됩니다. 예를 들어 판매 수치는 표가 아니라 `list_drip`으로 씁니다.

### 축이 맞아도 기사체 문장이면 버리도록 voice 규칙을 걸었습니다

축 조합이 맞더라도 문장이 기사체이면 실패입니다. 그래서 본문 문체(voice)에는 위반하면 결과를 버리는 규칙을 뒀습니다.

1.  **숫자 상한** — `data_brief`가 아니면 본문당 핵심 숫자는 2개 이하입니다. 변화율이나 여러 모델의 숫자를 나열하면 자동으로 버립니다.

2.  **첫 문장은 상황·감정·도발로 시작** — 데이터로 시작하지 않습니다.

3.  **본문에 링크 없음** — 출처는 댓글 각주에만 둡니다. 이유는 아래 예약 발행 절에서 설명합니다.

4.  **출처 커뮤니티 노출 금지** — "어느 커뮤니티에서 봤는데…" 같은 표현을 쓰지 않고 1인칭으로 다시 씁니다.

1편에서 설명한 **댓글 N<3 DROP 게이트**도 이 단계에서 동작합니다. 원본 게시물의 실제 댓글이 3개 미만이면 합성 댓글로 채우지 않고 그 소재를 버리는 규칙입니다.

### 결과: 게시물은 네 축의 조합과 voice 제약으로 정의됩니다

다섯 번의 수정을 거친 현재 생성 스킬은 게시물을 다음과 같이 정의합니다.

```plaintext
post = hook_engine × persona × format × (topic_tag*)   + voice (community vernacular, enforced)
```

> **설계 회고:** 4축은 처음부터 위에서 내려 설계한 구조가 아닙니다. 한 분류에 섞인 기준을 나누고, 자동화의 범위를 정하고, 빠져 있던 본문 형식 축을 채우는 과정을 차례로 거쳐 나온 구조입니다. 각 수정은 "이게 없으면 계속 같은 실패를 반복한다"는 관찰에서 시작했습니다. 콘텐츠 모델도 코드처럼 리팩터링 대상이라고 판단했습니다.

## 예약 발행에서 같은 글이 두 번 올라가지 않게 하려면?

### 발행 SaaS 대신 SQLite 큐와 1분 주기 워커를 만들었습니다

Buffer 같은 발행 SaaS를 쓰지 않고 직접 만들었습니다. Discord 봇과 VPS, SQLite가 이미 갖춰져 있었고, 필요한 기능은 슬롯 예약, 자동 발행, Discord 연동으로 단순했습니다. 외부 서비스를 붙이면 연동 지점과 비용이 함께 늘어납니다. 기존 구성에 **SQLite 큐 테이블과 1분 주기 cron 워커**를 더하는 쪽이 연동 부담과 비용 모두에서 낫다고 판단했습니다.

전체 흐름은 다음과 같습니다.

```plaintext
Discord: a human drops a source URL
   → generation skill: body + 3 comments + images
   → clarify buttons: [pick topic] [time: 14:23 / 19:47 / 🚀now]
   → threads_enqueue.py: INSERT into publish_queue (status=pending, scheduled_for)
        ┄┄┄ (async boundary) ┄┄┄
   → cron(1m) threads_publish_worker.py:
        atomically claim rows where scheduled_for ≤ now → 'publishing'
        → Threads Graph API publish (carousel ≤10)
        → update published (thread_url, published_at) + Discord notification
```

생성된 글은 `publish_queue`에 `pending` 상태로 들어갑니다. 실제 발행은 1분마다 실행되는 워커가 맡습니다. 큐에 넣는 쪽과 발행하는 쪽은 비동기 경계로 분리돼 있습니다.

### 워커가 발행 전에 행을 먼저 잠가 한 번만 발행되게 했습니다

워커는 1분마다 다시 실행됩니다. 같은 `pending` 행을 두 번의 실행이 함께 가져가면 같은 글이 두 번 발행됩니다.

그래서 워커는 발행 시각이 지난 행을 처리하기 전에, 원자적인 UPDATE 한 번으로 상태를 `publishing`으로 바꿉니다. 이 UPDATE로 상태를 바꾼 실행만 그 행을 발행합니다. 이미 `publishing`이 된 행은 다음 실행이 다시 가져가지 않습니다.

같은 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질을 **멱등성**이라고 합니다. 이 잠금 덕분에 워커가 1분마다 다시 실행돼도 이중 발행이 일어나지 않습니다.

### 발행 시각은 고르게 하고, API 한도에 맞춰 속도를 제한했습니다

-   **발행 시각 추천** — 사람이 시간을 직접 입력하지 않도록 KST 10:00–24:00 사이의 두 슬롯과 "지금(now)"을 버튼 세 개로 제공합니다.

-   **Rate limit** — Threads API는 계정당 24시간에 250건까지 허용합니다. 큐에서 꺼내 발행하는 속도에도 그에 맞춘 상한을 뒀습니다.

### 성과 매칭이 깨지지 않도록 본문에 링크를 넣지 않습니다

앞의 voice 규칙에서 본문 링크를 금지한 이유는 측정과 관련이 있습니다. 성과 수집 cron은 Threads에 _발행된 본문_과 _DB에 저장된 본문_을 문자 단위로 비교해서, 수집한 지표가 어느 게시물의 것인지 연결합니다. 본문에 링크가 있으면 이 비교가 깨집니다.

그래서 본문은 순수 텍스트로 두고, 외부로 나가는 링크는 모두 댓글 각주로 보냅니다. 생성 규칙처럼 보이지만, 다음 절의 측정 정확도를 위해 일부러 두 단계를 묶은 결정입니다.

## 게시물 클릭 중 실제 사람의 방문은 어떻게 구분할까?

이 절에서 가장 어려웠던 부분은 대시보드 시각화가 아니었습니다. 중복 집계와 봇 클릭이 숫자에 섞이지 않도록, 화면이 읽는 데이터의 형태 자체에서 막는 일이었습니다.

<a id="31-왜-직접-측정하는가--3계층-측정-경계"></a>

### Threads가 알려 주지 않는 클릭과 전환을 직접 기록했습니다

어떤 사람이 게시물을 보고 프로필의 bio 링크를 눌러 랜딩 페이지에 들어간 뒤 견적을 요청했다고 가정해 보겠습니다. Threads 인사이트가 알려 주는 것은 노출, 참여, 팔로워까지입니다. 마케팅 채널에서 정말 궁금한 "클릭이 나왔는가, 그리고 전환됐는가"는 플랫폼 밖에서만 답할 수 있습니다.

그래서 측정을 세 계층으로 나눴습니다.

```plaintext
Layer 3 conversion ← quote / topup        [only via PG / quote events]
Layer 2 click      ← go-redirect self-redirect  [not provided by Threads]
Layer 1 engagement ← hourly 6 metrics (views/likes/replies/reposts/quotes/shares)  [Threads API]
```

Threads가 책임지는 범위는 노출에서 프로필 방문까지입니다. 그 뒤의 bio 클릭, 랜딩, 전환은 자체 클릭 ID인 `cid`로만 추적합니다.

1.  bio 링크는 `go.차이사.com/{slug}` 리다이렉터를 가리킵니다. 리다이렉터는 클릭을 기록하고 `cid`를 발급합니다.
2.  302 리다이렉트로 랜딩 페이지에 `cid`를 넘기고, 랜딩 페이지는 이를 쿠키에 저장합니다.
3.  전환이 일어나면 같은 `cid`를 담아 전환 이벤트(`/conv`)를 보냅니다. 이 전달 과정도 같은 이벤트가 여러 번 와도 결과가 달라지지 않게(멱등하게) 처리합니다.

이렇게 클릭과 전환이 어느 게시물·링크에서 왔는지 연결하는 일을 **어트리뷰션(attribution)**이라고 합니다. 이 글의 3계층 어트리뷰션은 참여·클릭·전환을 서로 다른 출처에서 측정하고, 클릭과 전환을 `cid`로 잇는 구조입니다.

### 기록된 클릭의 약 90%가 봇이라 분석보다 상태 확인을 먼저 만들었습니다

대시보드 설계는 네 가지 관점을 병렬로 검토한 뒤 조율하는 방식으로 진행했습니다. 관리자 UX, 광고·전환, PM·정보 구조, 플랫폼 운영입니다. 그리고 모든 결정은 실제 데이터 스냅샷에 근거했습니다.

> 스냅샷: 게시물 44개 발행(계정 1개), 유효 클릭 13개, **봇 클릭 126개(≈90%)**, 전환 0개.

데이터가 거의 비어 있는 상태였습니다. 그래서 MVP의 첫 가치는 분석이 아니라 다음 세 가지를 보여 주는 것으로 정했습니다.

-   파이프라인이 살아 있는가
-   봇이 90%인 상황에서 봇 필터를 믿을 수 있는가
-   bio 링크가 아직 적용되지 않았다는 사실

hook×format 히트맵 같은 학습형 분석은 표본이 쌓일 때까지 미뤘습니다.

### 빈 데이터와 봇 클릭 때문에 숫자를 잘못 읽지 않게 했습니다

스냅샷에서 나온 결정은 네 가지입니다.

**(1) 데이터가 없는 상태를 정상 상태로 설계했습니다.** 전환이 0개일 때 화면이 깨지거나 오해를 주면 안 됩니다. 모든 위젯에는 데이터가 없을 때의 안내 문구(empty state)와 표본 크기 `n` 배지를 붙였습니다. `n`이 5 미만이면 노랑, 0이면 회색입니다. 봇 비율은 항상 표시합니다. 빈 상태는 수집 중, 표본 부족, 빈 버킷, 미연결의 네 가지로 구분합니다.

**(2) "전환 0개"가 버그가 아님을 먼저 확인했습니다.** `/conv` 수집, 토큰, 302의 `cid` 전달, 랜딩 쿠키까지 전체 경로를 실제 환경에서 검증해 파이프라인이 정상임을 확인했습니다. 전환 POST가 0건인 것은 아직 실제 결제나 견적이 없다는 뜻입니다. 그래서 전환 화면은 "수집 대기" 상태로 시작합니다. 운영자가 빈 화면을 장애로 오인하지 않게 하려는 설계입니다.

**(3) 매출 중복 집계를 스키마에서 막았습니다.** 파트너 충전금(`topup`, 선불)과 고객 견적(`quote`, 실현 매출)을 더하면 매출이 부풀려집니다. 그래서 "총매출" 컬럼을 의도적으로 두지 않았습니다. 실현 매출 `SUM(quote.value)`과 충전 유입 `SUM(topup.value)`은 따로 떨어진 두 행으로만 보여 줍니다. 레이아웃에도 합계 칸을 두지 않아 덧셈할 자리를 처음부터 없앴습니다. ROAS의 분자는 quote만 사용합니다.

**(4) 봇을 제외한 값을 기본 분모로 삼았습니다.** 봇이 약 90%인 상황이므로 클릭·전환 지표는 기본으로 `is_bot=0`인 클릭만 셉니다. 같은 `ip_hash`와 `slug` 조합은 24시간 안에 한 번만 셉니다. 분모를 얼마나 믿을 수 있는지 보이도록 CVR 옆에 어트리뷰션되지 않은 비율(unattributed-rate) 배지를 둡니다.

### 모든 화면이 같은 VIEW만 읽게 해 규칙을 한 곳에 고정했습니다

대시보드는 소스 테이블을 직접 읽지 않습니다. 모든 화면은 정해진 VIEW를 거쳐 데이터를 읽고, 집계는 쿼리 시점에 계산합니다. 어떤 컬럼을 어떤 의미로 내놓을지 VIEW에서 정하므로, 이 VIEW가 화면과 데이터 사이의 **데이터 계약** 역할을 합니다. 앞에서 정한 "총매출 컬럼 없음"과 "봇 제외 기본값"도 이 계약 안에 들어 있습니다.

데이터가 작아서 집계 테이블을 미리 만들어 두는 구체화는 미뤘습니다. 임계치에 도달하면 전환할 계획입니다. 두 DB(`clicks.db ⨝ editorial.db`)의 조인은 SQLite의 `ATTACH`로 처리합니다.

```plaintext
v_funnel_daily (account × audience × day):
  clicks(is_bot=0) | quote_cnt, quote_value | topup_cnt, topup_value | follower_ctr
  ※ a 'total_revenue' column is intentionally absent → blocks summation at the source
age-normalization: ROW_NUMBER() OVER(PARTITION BY short_id ORDER BY ABS(age_hours-24))
                   — no raw cumulative sort (avoids unfair comparison across post ages)
```

아래쪽 `age-normalization`은 발행 후 경과 시간이 다른 게시물을 공정하게 비교하기 위한 처리입니다. 누적 수치를 그대로 정렬하지 않고, 게시물마다 발행 후 24시간에 가장 가까운 시점의 값을 골라 비교합니다.

### 작은 규모에 맞춰 스택을 골랐습니다

| 항목 | 선택 | 근거 |
| --- | --- | --- |
| 배치 | go-redirect에 `/admin/*` 라우터 추가(별도 컨테이너 없음) | 읽기 전용, 데이터 충돌 없음. 분리 이득 < 복잡도 |
| 렌더 | FastAPI + Jinja2 SSR | 사용자 소수 · 6개 뷰. SPA는 오버엔지니어링 |
| 차트 | Chart.js (CDN) | 빌드 제로; bar/line/scatter/heatmap 커버 |
| 집계 | SQLite VIEW + 쿼리 시점 계산 | 소규모; 구체화는 미룸 |
| 인증 | traefik basicAuth | 운영자 소수; 앱 측 인증 코드 제로 |
| DB | `mode=ro` + `query_only=ON`, ATTACH | WAL 동시 읽기 → 수집기 cron의 쓰기와 충돌 없음 |

구현하면서 두 가지 함정을 만났습니다.

1.  editorial.db를 `:ro`로 bind-mount하면 WAL 읽기에서 `disk I/O error`가 납니다. 마운트는 rw로 두고, 앱의 DB 커넥션에서만 읽기 전용으로 열어 해결했습니다.
2.  go-redirect의 `@app.get("/{slug}")` catch-all 라우트가 모든 경로를 가져갑니다. `/admin/*` 라우터를 그보다 먼저 선언해야 합니다.

개요 화면의 위젯은 세 개입니다. 퍼널 워터폴(views→clicks→conversions), 봇 비율, 데이터 신선도(freshness)입니다. 이 화면은 매일 "파이프라인은 살아 있고, 클릭의 90%는 봇이며, bio 링크를 적용해야 한다"는 상태를 보여 줍니다. 매일 가장 먼저 확인할 신호 하나를 보여 주는 것이 MVP의 목적입니다.

## 마무리하며

<a id="회고"></a>
<a id="5-회고"></a>

-   **콘텐츠 모델도 리팩터링 대상이었습니다.** 한 enum에 섞인 기준을 독립된 축으로 나누고, 빠져 있던 본문 형식 축을 채운 과정은 코드 리팩터링과 같은 흐름이었습니다. "왜 매번 같은 방식으로 실패하는가"를 추적하면 빠진 축이 드러났습니다.

-   **모델을 바꾸면 데이터도 옮겨야 했습니다.** 발행 원장의 검증 로직은 학습 루프와 숨어서 연결된 지점이었습니다. 스키마나 어휘를 바꿀 때는 과거 데이터의 정규화도 함께 설계해야 합니다.

-   **직접 만들지, 도입할지는 연동 부담으로 판단했습니다.** 발행 SaaS 대신 큐와 cron을 택한 결정적 이유는 비용보다 연동 부담이었습니다. 기존 Discord·DB·cron을 그대로 쓰고, 멱등 워커로 구조를 단순하게 유지할 수 있었습니다.

-   **측정의 정확성은 화면보다 스키마에서 지켰습니다.** 중복 집계는 총매출 컬럼을 없애서, 봇 오염은 `is_bot=0`을 기본 분모로 삼아서 막았습니다. 데이터 계약에서 강제하면 화면 단계의 실수를 미리 막을 수 있습니다.

-   **다음 단계:** 표본이 충분해지면 hook×format 히트맵으로 스스로 개선하는 루프를 닫겠습니다. 실제 전환이 생기면 `cid` 캡처율과 어트리뷰션되지 않은 비율을 기준으로 어트리뷰션 품질을 다듬겠습니다.

두 편을 관통하는 생각은 하나입니다. **봇 콘텐츠에서 "자동 생성의 흔적"은 신뢰 비용입니다.** 1편은 안티봇 위협 모델, 2편은 콘텐츠의 진정성과 측정의 정확성을 다뤘습니다. 둘 다 같은 질문으로 이어집니다. 사람이 검증된 소재를 고르고, 봇이 변환하고, 시스템이 발행과 측정을 자동화하는 구조에서 **경계를 어디에 그을 것인가**입니다.

## 들어가며

2026년 10월, NCP에서 운영하던 그룹웨어 WITIM을 다른 계정으로 옮겼다. Terraform으로 인프라를 다시 구성하고 NKS에 서비스를 올린 뒤, 데이터와 배포 경로까지 전환했다. 실제 사용자 영향은 약 13분이었다.

클라우드 크레딧을 활용하기 위해 WITIM 운영 환경을 새 NCP 계정으로 옮겨야 했다. WITIM은 이미 NKS(Naver Kubernetes Service)에서 운영 중이었다. 해야 할 일은 Kubernetes 도입이 아니라, 기존 서비스와 데이터를 새 계정으로 옮기고 배포·모니터링까지 다시 연결하는 작업이었다.

이전 담당자는 작업을 진행하다 퇴사했다. 먼저 남겨진 인프라 문서와 이전 계획, PR을 읽었다. 그런데 문서에 적힌 구조와 실제 리소스가 맞지 않았다. 이전에 생성했던 새 계정 리소스 일부는 이미 삭제돼 있었고, 기존 계정에는 VM 시절의 로드밸런서와 사용이 끝난 서비스가 남아 있었다. Terraform state에도 실제로 존재하지 않는 리소스가 있었다.

그전까지는 새 계정에 필요한 자원을 다시 만들면 이전이 시작될 거라고 생각했다. 하지만 **Terraform에 적힌 자원과 실제로 남아 있는 자원이 다르다면 `apply`가 복구인지 재생성인지부터 불분명해진다.** 실수로 기존 자원을 교체하는 것도 위험하지만, 더 이상 쓰지 않는 서비스를 새 계정에 다시 만드는 것도 문제였다.

그래서 바로 구성을 시작하지 않고 이전 담당자의 문서·PR·Git 이력부터 읽었다. 당시 리소스의 실제 상태는 NCP 콘솔과 API, Kubernetes, Terraform state를 통해 다시 확인했다. **확인된 현재 상태를 기준으로 이전 범위를 정하고, 재구성·데이터 이전·리허설·운영 전환 순서로 진행했다.**

## 1. 이전 대상은 Terraform 코드가 아니라 실제 운영 환경을 기준으로 정했다

WITIM의 운영 방식은 몇 달 사이에 바뀌었다. 4월에는 VM과 오토스케일링 그룹을 사용했고, 6월 말부터는 NKS와 ArgoCD로 배포했다. 그런데 VM 시절의 로드밸런서가 여전히 남아 있었고, 사용이 사실상 끝난 별도 서비스도 노드풀을 차지하고 있었다.

운영 문서는 작성 시점마다 설명하는 구조가 달랐다. 예를 들어 4월 문서에는 VM이 직접 컨테이너 이미지를 받아 실행하는 흐름이, 이후 문서에는 ArgoCD가 Git에 기록된 이미지 태그를 읽어 NKS에 배포하는 흐름이 남아 있었다. 둘 다 한때는 맞는 설명이었지만, 10월의 실제 운영 구조를 판단하는 기준으로 함께 쓸 수는 없었다.

Git 이력으로 구조가 바뀐 시점을 확인하고, 실제 서비스가 연결된 로드밸런서와 NKS 워크로드를 대조했다. 각 서비스에 트래픽이 들어오는지, 연결된 노드가 있는지, 지금도 배포 대상인지 살펴봤다. **자원이 존재하는 것과 운영에 필요한 것은 다른 문제**였다.

이전 범위는 다음과 같이 정리했다.

| 구분 | 결정 | 이유 |
| --- | --- | --- |
| WITIM 본체·실시간 서버·로그인 서비스 | 이전 | 실제 사용자가 이용하는 서비스 |
| PostgreSQL·Redis | 이전 | 메시지, 근태, 세션과 사용량 기록 보존 필요 |
| ArgoCD·로그·알림·배포 파이프라인 | 이전 및 재구성 | 서비스가 실행되는 것과 계속 운영 가능한 것은 다름 |
| 예전 Orbit 서비스·시험용 관리자 앱 | 새 계정에는 만들지 않음 | 현재 운영 범위에서 제외할 수 있음 |
| VM 시절 로드밸런서 등 잔여 자원 | 이전 제외 | 더 이상 서비스 트래픽을 처리하지 않음 |

새 계정의 Terraform state에도 이미 삭제된 리소스 9개가 남아 있었다. 코드·state·실제 리소스 사이에 차이가 있으면, 이후 `plan`의 생성·삭제·교체 목록도 해석하기 어려워진다. 실제로 존재하지 않는 항목을 state에서 정리한 뒤 다시 계획을 확인했다. 없는 리소스를 state에서 정리하는 것과 실제 클라우드 자원을 삭제하는 작업은 분리해 처리했다.

이 과정을 거쳐 이전 범위를 확정했다. **기존 계정의 모든 것을 복제하지 않고, 현재 운영에 필요한 자원만 새 계정에 만들기로 한 것**이 첫 번째 결정이었다.

## 2. Terraform은 재구성 도구이면서 변경을 검증하는 도구였다

10월 21일 새 계정에 네트워크, bastion, 관리형 PostgreSQL·Redis, NKS를 구성했다. NKS는 공통 운영 구성요소용 `system` 1대, 앱용 `witim` 2대, 실시간 서버용 `centrifugo` 2대로 시작했다. 총 5대이고, 노드풀 자동 확장 설정을 두었다.

기존 계정을 그대로 복제하지 않은 이유가 있다. 이전 환경에서는 별도 서비스의 노드풀에 운영 도구가 함께 올라가 있는 등, 현재 역할과 자원 이름이 맞지 않는 부분이 있었다. 새 환경에서는 ArgoCD와 로그·알림을 위한 공통 노드와 앱·실시간 서버의 노드풀을 분리했다. 어디에 무엇이 올라가야 하는지 더 쉽게 확인하고, 이후 노드 수를 조정할 때 영향 범위를 예측하기 위한 구분이었다.

Terraform은 VPC·서브넷·bastion·관리형 DB·Redis·NKS처럼 **계정에 속하는 기반 자원**을 구성하는 데 사용했다. 반면 클러스터 안에서 계속 변경되는 애플리케이션 매니페스트는 ArgoCD가 Git을 기준으로 동기화하도록 유지했다. 인프라를 만드는 도구와 앱을 배포하는 도구의 책임을 나눴다.

네트워크도 데이터 이전 방식과 함께 결정했다. 두 계정 사이에 VPC Peering을 추가하면 DB를 직접 복제하기는 편해진다. 다만 이번에는 데이터가 작고, 이전 후에는 필요하지 않을 연결이었다. 계정 사이에 상시 접근 경로를 만들지 않고 각 클러스터 내부의 임시 파드로 데이터를 옮기기로 했다.

Terraform 적용 중에는 NKS 노드풀의 taint 설정에서 API 오류가 발생했다. Terraform이 해당 리소스를 교체 대상으로 표시했지만, 정상 동작하는 노드를 실제로 교체하면 오히려 문제가 커질 수 있었다. API 상태와 리소스 실체를 확인한 결과 재생성은 불필요했다. `terraform untaint`로 표시를 해제하고 `plan`에서 교체가 발생하지 않는지 재확인했다. **교체하지 않아도 된다는 사실을 확인한 뒤 선택한 조치**였지, taint 오류에 일괄적으로 적용할 해결책은 아니었다.

`terraform apply`가 성공했는지만 보는 것보다 **무엇을 새로 만들고, 무엇을 교체하지 않았는지** 확인하는 일이 중요했다.

## 3. 새 클러스터만으로는 배포할 수 없었다

NKS와 DB가 준비된 뒤에는 애플리케이션이 새 계정에서 배포되고 업데이트되는 경로를 연결했다.

```text
GitHub Actions → 새 NCP Container Registry
             → Git 이미지 태그 갱신
             → ArgoCD → 새 NKS
```

먼저 기존 레지스트리의 이미지를 새 레지스트리로 옮겼다. 롤백에 쓸 이미지까지 포함해 다섯 개를 복사하고 해시를 대조했다. 전환 당일에 이미지를 새로 빌드하거나 옛 계정에서 가져올 필요가 없도록 하기 위해서였다. 이미지가 있다는 사실보다 **새 노드에서 실제로 pull할 수 있는지**까지 확인해야 했다. 레지스트리 주소와 인증 키가 동시에 바뀌기 때문이다.

배포 권한도 손봤다. 기존 ArgoCD는 퇴사자의 개인 GitHub 토큰으로 저장소에 접근하고 있었다. 계정이 제거되면서 토큰이 무효화돼 배포와 롤백이 멈춰 있었다. 여기서 곧바로 새 토큰을 넣으면 멈춰 있던 동기화가 재개되면서, 그동안 쌓인 Git 변경이 한꺼번에 운영 환경에 반영될 수 있었다.

따라서 먼저 자동 동기화를 비활성화하고, 개인 토큰을 조직 소유의 **읽기 전용 GitHub App**으로 바꿨다. 앱의 저장소 접근과 동기화 상태를 확인한 다음에만 필요한 배포를 진행했다. 로그인 서비스에서는 재발급된 NCP 키가 이미지 pull Secret에 반영되지 않아 401 오류가 났다. Secret을 교체하고 **다른 노드에서 이미지를 실제로 내려받는 것**까지 확인했다. 운영 파드의 재시작은 발생하지 않았다.

전환 후 운영 배포를 다시 실행했을 때는 다른 문제가 드러났다. GitHub의 `main` 브랜치 규칙이 자동 배포 과정의 이미지 태그 갱신 커밋을 막고 있었다. CI에서 이미지를 만드는 단계가 성공해도, Git에 새 태그를 쓰지 못하면 ArgoCD는 변경을 인식하지 못한다. 즉 **빌드 성공과 실제 배포 성공을 구분해야 하는 상황**이었다.

브랜치 보호 규칙을 느슨하게 만드는 대신, 해당 저장소의 이미지 태그만 갱신할 수 있는 별도 GitHub App을 만들고 이 앱에만 예외를 허용했다. 10월 23일 15시 32분, 새 경로로 web과 admin 배포를 마쳤다.

배포 전에 운영 데이터 복사본으로 DB 마이그레이션도 재현했다. 그 과정에서 사전 적용해야 할 인덱스 11개가 빠져 있다는 것을 발견했다. 그대로 배포했다면 마이그레이션 사전 검사에서 멈췄을 것이다. 인덱스를 먼저 적용하고 유효성을 확인한 뒤, 마이그레이션 48개를 오류 없이 실행했다.

ArgoCD 동기화 때 web 파드가 일시적으로 1대까지 줄어드는 문제도 `RespectIgnoreDifferences` 설정을 수정해 해결했다. **새 서버에서 한 번 실행되는 것**과 **그다음 배포도 안전하게 되는 것**은 별개의 검증 항목이었다.

## 4. 전환 당일에는 데이터와 트래픽만 옮기도록 준비했다

앱은 새 클러스터에 같은 이미지를 올리면 된다. 반면 DB는 두 계정에서 동시에 쓰기를 받게 해서는 안 된다. 메시지는 옛 DB에, 근태 기록은 새 DB에 남는 상황을 피해야 했다.

PostgreSQL 논리 복제도 검토했지만, 덤프 크기가 약 46.5MB였고 리허설에서 복원 시간이 짧게 나왔다. 복제 슬롯과 계정 간 네트워크를 추가로 관리하는 것보다 **사전에 충분히 검증하고 짧게 쓰기를 멈추는 방식**이 이번 규모에 적합했다. PostgreSQL 버전도 17로 올리지 않고 기존과 같은 15.15로 유지했다. 계정 이전과 DB 업그레이드를 한꺼번에 진행할 이유가 없었다.

10월 22일 리허설에서는 운영 DB를 읽기 전용으로 덤프하고 새 환경에 복원했다. 실제 데이터로 로그인, 채팅, 파일 기능을 확인했다. worker는 외부 통신을 차단한 상태에서 시험했다. 당시 발견한 설정 문제도 전환 전에 수정했다.

여기서 되돌리기 기준도 미리 정했다. 새 환경에서 사용자 쓰기가 시작되기 전에는 기존 환경을 다시 켜는 방식으로 복귀할 수 있다. 하지만 새 DB에 기록이 쌓인 뒤에는 주소만 옛 계정으로 되돌리면 데이터가 빠질 수 있다. 따라서 데이터 대조와 새 앱 점검을 통과한 뒤에만 외부 진입점을 변경하도록 순서를 고정했다.

실제 전환은 다음 순서로 진행했다.

```text
10월 22일 23:59  기존 환경 쓰기 중지
10월 23일 00:01–00:05  PostgreSQL·Redis 최종 이전
10월 23일 00:06  새 환경 앱 기동
10월 23일 00:12  Cloudflare 진입점 5개 전환 완료
```

| 확인 항목 | 결과 |
| --- | --- |
| PostgreSQL | 285개 테이블, 495,192행 일치 |
| Redis | 9,587개 키 일치 |
| 사용자 영향 | 약 13분 |
| 전환 후 1시간 웹 요청 | 5,518건 중 5xx 0건 |
| 같은 기간 worker 처리 | 1,926건 성공, 재시작 0회 |

전환 직후 웹뿐 아니라 데스크톱·모바일 로그인 유지, 실시간 채팅, 파일, 푸시까지 확인했다. 로그인 세션을 유지하고 데이터가 일치한다는 사실은 사용자에게 중요한 결과였다. 다만 **전환 직후 기능 확인과 이후의 안정적인 운영은 같은 검증이 아니다.** 같은 날 운영 배포를 끝까지 실행하고, 모니터링 경보와 백업도 새 계정 기준으로 점검했다.

11월 2일에는 옛 계정의 로그를 보존하고 Loki 보관 기간을 30일에서 90일로 늘린 뒤, 옛 계정 리소스를 모두 정리했다. 이전 계정의 10월 인프라 사용액은 약 134만 원이었고, 정리 후에는 남아 있는 과금 자원이 없도록 했다. 이 금액은 당시 옛 계정의 사용액이지, 그대로 절감한 순비용을 뜻하지는 않는다.

## 마무리하며

이번 이전에서 오래 걸린 건 Terraform 코드를 작성하는 일만이 아니었다. 실제 운영 상태와 다른 설정을 찾아내고, 유지할 자원과 없앨 자원을 고르고, 배포 권한부터 데이터 전환 순서까지 다시 확인해야 했다.

처음부터 기존 구성을 복제했다면 더 빨리 시작할 수는 있었을 것이다. 대신 필요 없는 자원과 이미 고장 난 배포 경로까지 가져왔을 가능성이 높다. 사전 점검과 리허설에 시간을 쓴 덕분에 전환 당일에는 데이터 복사와 트래픽 변경에 집중할 수 있었다.

이전의 성공 기준을 **새 NKS가 뜨는 것**이 아니라 **새 계정에서 배포·복구·관측까지 이어지는 것**으로 잡은 점이 가장 중요했다.

# jieun.dev 기술 블로그 집필 기준

## 독자와 목표

독자는 개발 경험이 있지만 이 프로젝트, 회사 내부 용어, 이전 글을 모른다. 독자가 글을 읽고 문제의 맥락, 설계 선택의 근거, 확인한 결과와 한계를 설명할 수 있게 쓴다.

이 기준은 [참고 글 5편](README.md)에서 얻은 편집 원칙을 jieun.dev에 맞게 정리한 것이다. 모든 글의 바깥 구조는 `들어가며 → 주제별 본론 → 마무리하며`로 통일한다. 본론의 소제목과 전개는 회고, 기술 해설, 장애 분석, 비교 실험에 맞춰 선택한다.

## 한국어 글의 문체 규칙

새 글과 기존 글 수정 모두 설명 문장을 **`~습니다·~입니다` 문체**로 작성합니다. LY 기술 블로그처럼 독자에게 차분하게 설명하는 말투를 유지합니다.

문체의 구체적인 참고는 [Tech-Verse 2026 참관기](https://techblog.lycorp.co.jp/ko/tech-verse-2026-ai-driven-development-review)입니다(2026-09-23 본문 확인). 아래는 이 레포에서 채택한 편집 기준이며 LY의 공식 작성 규정은 아닙니다. 원문의 문장을 복사하거나 작성자의 경험을 가져오지 않습니다.

- **어미보다 설명 방식을 먼저 봅니다.** 상황과 배경을 알려 준 뒤 관찰한 문제, 판단의 이유, 확인한 결과를 연결합니다. 독자가 앞선 글이나 내부 용어를 안다고 가정하지 않습니다.
- **담담하고 구체적으로 씁니다.** 자극적인 비유나 평가 대신 어떤 조건에서 무엇이 실패했는지 설명합니다. 예를 들어 `메모리가 터집니다`보다 `메모리 한도를 초과할 수 있습니다`처럼 동작과 제약을 드러냅니다. 가능성·실측 여부는 원래 근거에 맞춥니다.
- **독자에게 안내하되 과하게 말을 걸지 않습니다.** `이 글에서는 …을 소개합니다`, `이를 확인하기 위해 …을 비교했습니다`처럼 설명을 연결합니다. 질문형 소제목은 이해를 돕는 곳에서만 자연스럽게 사용하고, 모든 문장을 딱딱한 보고서 표현으로 바꾸지 않습니다.
- **관찰과 생각을 구분합니다.** 직접 확인한 결과는 근거와 함께 쓰고, 해석이나 느낀 점은 `…라고 판단했습니다`, `…라는 점이 인상적이었습니다`처럼 작성자의 판단임을 밝힙니다. 과장된 성과나 새로운 인과관계를 덧붙이지 않습니다.
- **한 문장에 단계를 과하게 넣지 않습니다.** 입력·처리·결과가 길게 나열되면 문장을 나누고, 핵심 행동과 의미가 먼저 읽히게 다듬습니다.

- 본문, 요약(description), 문장형 이미지 설명·캡션, 목록과 표 안의 완결된 설명 문장, 작성자가 쓴 콜아웃에 적용합니다. `~한다·~이다`체나 `~해요`체를 섞지 않습니다.
- 과거 경험은 `~했습니다`, 현재 동작은 `~합니다`, 한계는 `~확인하지 못했습니다`처럼 시제와 주장의 강도를 보존합니다. 문체를 바꾸면서 계획을 성과로 바꾸거나 추정을 단정하지 않습니다.
- 작성자의 1인칭은 필요한 경우 `저는·제가`로 씁니다. 주어가 명확하면 생략합니다.
- 제목·소제목·부제·이미지 alt·표 항목의 짧은 명사형 표현은 억지로 문장으로 늘리지 않습니다. 소제목이 완결된 서술문이라면 같은 문체를 적용하고, 기존 문단 링크를 보존합니다.
- 코드, 코드 주석, 로그, 명령어, 실제 UI 문구, 프롬프트, 사용자의 발언 등 직접 인용은 원문을 유지합니다. 인용을 설명하는 작성자의 문장은 정중한 문체로 씁니다. Markdown 인용 블록이라고 모두 직접 인용은 아니므로 작성자의 요약·설명은 통일합니다.
- 영어 글에는 한국어 종결어미 규칙을 적용하지 않습니다.
- 자동 치환만으로 끝내지 않습니다. `~했다는`, `~한다고` 같은 문장 내부 표현과 인용을 훼손하지 않았는지 읽어 보고, 남은 평서체·해요체가 예외에 해당하는지 확인합니다.

예: `작업을 큐로 분리했다. 요청은 더 이상 완료를 기다리지 않는다.` → `작업을 큐로 분리했습니다. 요청은 더 이상 완료를 기다리지 않습니다.`

## 모든 글의 공통 구조

사용자가 지정한 [Tech-Verse 2026 참관기](https://techblog.lycorp.co.jp/ko/tech-verse-2026-ai-driven-development-review)의 도입·본론·마무리 구성을 따른다. 원문 확인일은 2026-09-23이다. 기존 5편은 본론 전개의 참고 자료로 유지한다.

- 한국어 글의 첫 H2는 `## 들어가며`, 마지막 H2는 `## 마무리하며`로 쓴다. 영어 글은 각각 `## Introduction`, `## Conclusion`으로 대응한다.
- 들어가며에는 제품·사용자·작성자의 역할, 문제의 배경과 이번 글에서 다룰 질문을 설명한다. 요약 콜아웃이 있다면 이 절 안에 둔다.
- 본론에는 내용을 드러내는 H2 소제목을 사용한다. `## 본론`이라는 제목으로 모든 내용을 한 번 더 감싸지는 않는다. 배경·문제·판단·구현·검증의 연결이 드러나도록 구성한다.
- 마무리하며에는 본론에서 확인한 결과, 판단의 의미, 남은 한계나 다음 과제를 간결하게 정리한다. 새로운 구현 설명이나 검증되지 않은 성과를 처음 소개하지 않는다.
- 기존 글의 결과·구현 절이 상세하다면 본론에 유지하고 별도 마무리를 쓴다. 이미 결론 역할을 하는 회고·교훈 절은 제목을 통일하고 내용을 다듬는다. 제목만 붙이고 도입이나 결론을 비워 두지 않는다.
- 참고 자료나 시리즈 안내가 끝에 필요하다면 마무리 절 안의 H3 또는 짧은 목록으로 둔다. 코드 블록 속 제목은 글의 목차로 취급하지 않는다.
- 기존 제목을 바꿀 때는 해당 제목의 기존 앵커를 가능한 한 보존해 공유된 문단 링크가 끊기지 않게 한다.

```markdown
## 들어가며

제품과 사용자, 문제의 배경, 이 글의 핵심 질문을 소개합니다.

## [문제 또는 배경을 설명하는 제목]

## [판단과 구현을 설명하는 제목]

## [검증 결과를 설명하는 제목]

## 마무리하며

확인한 결과와 의미, 한계 또는 다음 과제를 정리합니다.
```

## 글을 구성하는 원칙

1. **배경을 먼저 제공한다.** 도입부에서 제품이 무엇인지, 누가 어떤 입력으로 어떤 결과를 얻는지, 작성자가 맡은 범위와 이번 글의 질문을 설명한다. 서비스명과 운영 숫자만으로 배경을 대신하지 않는다.
2. **핵심 질문을 하나 정한다.** 각 절이 그 질문에 기여하는지 확인한다. 독립적인 질문이 둘 이상이면 분할을 검토한다. 날짜나 분량의 중간을 기계적으로 자르지 않는다. 후속 편에도 필요한 배경을 짧게 제공한다.
3. **독자의 이해 순서로 배열한다.** 사용 흐름이나 결과물, 기존 방식, 구체적인 문제, 판단, 구현, 검증의 관계를 보여준다. 개발 순서가 이해를 돕는 경우에는 시간순 구성을 유지한다.
4. **중요한 판단을 깊게 설명한다.** 실패한 입력·조건과 사용자 또는 시스템에 미친 영향을 보여주고, 어떤 관찰 때문에 다음 선택을 했는지 연결한다. 여러 문제를 같은 무게로 나열하지 않는다.
5. **대안을 실제 검토 범위 안에서 설명한다.** 당시 후보와 선택 기준에 기록이 있으면 제시한다. 나중에 떠올린 대안을 당시 검토한 것처럼 쓰지 않는다. 참고 글과 목차를 맞추기 위해 가상의 실패담을 만들지 않는다.
6. **추상적인 말에는 구체적인 동작을 붙인다.** 입력·출력, 상태 전이, 짧은 코드, 로그, 구성도 중 설명에 필요한 증거를 선택한다. 그림과 코드 앞에는 무엇을 볼지, 뒤에는 무엇을 알 수 있는지 설명한다.
7. **낯선 개념을 필요한 시점에 정의한다.** 내부 제품명은 기능과 역할로 풀어 쓴다. 긴 기술 목록이나 약어 사전을 도입부에 쌓지 않는다. 독자가 이미 아는 일반 개념까지 과도하게 설명하지 않는다.
8. **결과를 검증 범위 안에서 말한다.** 수치에는 대상, 시점, 조건과 비교 기준을 붙인다. 실측·추정·환산, 상관·원인, 검색 노출·유입, 구현·운영·계획을 구분한다. 검증하지 못한 항목은 남은 과제로 표시한다.
9. **주변 작업은 선별한다.** 핵심 판단을 설명하지 않는 작업은 축약하거나 관련 글로 연결한다. 감정적인 고백, 반복되는 교훈, 작성 과정을 길게 설명하는 문장은 논리의 빈칸을 채우지 못한다.
10. **작성자의 역할과 사실을 보존한다.** 전 회사 표현과 SEO 규칙은 루트 `CLAUDE.md`를 따른다. 조직의 결정과 본인의 구현·분석을 구분하고, 현재 글의 사실을 참고 글의 기술이나 성과로 대체하지 않는다.

## 작업 절차

### 1. 편집 범위와 근거 확인

대상 글을 읽고 독자, 핵심 질문, 근거로 사용할 코드·로그·측정·메모를 정리한다. [README](README.md)에서 적합한 참고 카드 1~2개를 읽는다. 외부 원문 재조회는 세부 확인이 필요할 때만 한다.

### 2. 목차 재구성

유지할 내용, 옮길 내용, 축약할 내용과 근거가 부족한 주장을 구분한다. 핵심 질문과 개요를 짧게 제시한다. 사용자에게 수정 실행을 요청받았다면 별도 목차 승인을 요구하지 않고 이어서 집필한다. 구성안만 요청받았다면 본문은 수정하지 않는다.

### 3. 집필

중요한 결정마다 다음 관계를 확인한다. 이는 본문에 그대로 붙일 고정 소제목이 아니다.

`기존 동작 → 구체적인 문제와 영향 → 관찰한 근거 → 선택한 변경 → 검증 결과와 한계`

사실이 부족한 부분은 추측으로 연결하지 않는다. 초안에서는 `[확인 필요: 어떤 자료가 필요한지]`로 표시하고 최종 보고에 남긴다. 공개용 완성본에는 확인되지 않은 주장을 확정적으로 넣지 않는다. 다른 부분은 확보된 근거로 계속 작성한다.

### 4. 처음 읽는 개발자 관점에서 검토

작성 후 별도 검토 패스에서 아래 질문에 본문 위치나 근거로 답하고, 부족한 부분을 수정한다. 형식적인 점수 합계로 품질을 판정하지 않는다.

| 검토 질문 | 통과 기준 |
| --- | --- |
| 한국어 설명 문장의 문체가 일관적인가? | 본문·요약·문장형 캡션·작성자의 콜아웃이 `~습니다·~입니다` 문체이며, 명사형 표현과 코드·직접 인용은 보존했다. |
| 어미만 바꾸지 않고 차분하게 설명하는가? | 배경·관찰·판단의 연결이 드러나고, 과한 구어체·비유·단정을 구체적인 설명으로 다듬었다. |
| 모든 글의 공통 구조를 따르는가? | 첫 H2가 들어가며, 마지막 H2가 마무리하며이고 사이에 주제별 본론이 있다. 영어는 Introduction·Conclusion을 사용한다. |
| 도입부만으로 제품과 사용 흐름을 알 수 있나? | 사용자·입력·결과와 글의 범위를 설명한다. |
| 글 전체가 무엇에 답하는지 분명한가? | 핵심 질문이 하나이고 각 절이 그 질문에 기여한다. |
| 문제가 구체적인가? | 발생 조건, 기존 동작, 영향이 드러난다. |
| 왜 그 방법을 선택했는가? | 관찰 또는 명시한 제약이 선택으로 연결된다. |
| 구현을 이해할 수 있나? | 해당 판단을 설명하는 동작·예시·코드·그림이 있다. 모든 종류가 필요한 것은 아니다. |
| 결과를 믿을 근거가 있나? | 측정 조건과 비교 기준, 검증하지 못한 범위를 구분한다. |
| 처음 보는 용어 때문에 막히지 않나? | 필요한 용어를 첫 등장 부근에서 설명한다. |
| 삭제해도 논리가 유지되는 부분이 있나? | 중복과 주변 작업을 줄인다. |
| 관찰과 해석이 섞이지 않았나? | 단정의 강도가 근거의 강도를 넘지 않는다. |

### 5. 파일 검증과 보고

게시물을 수정했다면 `npm run build`로 컬렉션과 frontmatter 오류를 확인한다. 이동·분할 시 기존 URL과 한국어/영어 연결의 영향을 확인한다. 링크, 이미지 설명, 수치의 표기와 출처도 살핀다.

마무리에는 달라진 구조, 실제 검증 결과, 여전히 필요한 사실 자료를 간단히 알린다. 승인된 수정 전후 사례가 생기면 참고 자료에 축적한다. 집필 참고 문서만 수정했다면 상대 링크와 변경 범위를 확인하는 것으로 충분하다.
